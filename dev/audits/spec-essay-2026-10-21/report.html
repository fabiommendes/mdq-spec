Strengths and weaknesses

Strengths

  • Grammar violations: The essay tag literal "[essay]" agrees with the bracketed-tag rules of question-base.md:211-217: tested with Lark, it accepts [essay] and rejects [ essay ] (whitespace inside brackets), [Essay] (case), [essay] write here, [essay]\nwrite here (more than a single tag) and [essay](http://x) (a link). mdq-py gives the same result for each of these inputs. (docs/question-types/essay.md:34-36)
  • Omissions: The essay corpus covers the tag variants and misplacements: spaced, uppercase, NBSP-indented, indented, in a list, in a blockquote, with trailing text, repeated, and an answer key before the body or repeated. (examples/invalid/essay-spaced-tag.mdq.md, examples/invalid/essay-tag-uppercase.mdq.md, examples/invalid/essay-tag-in-list.mdq.md, examples/invalid/essay-two-tags.mdq.md, examples/invalid/essay-two-answer-keys.mdq.md, examples/valid/essay/indented-tag.mdq.md)
  • Schema mismatches: schema/essay.yaml agrees with essay.md on the input enum and its default text, on highlight being ignored with a warning for non-code input, and on answerKey blank-text. (schema/essay.yaml:16-48)
  • Inconsistencies: The essay lint codes in essay.md agree with docs/lint-codes.md in name, level and scope (ignored-highlight, unknown-highlight-language, code-input-without-highlight, missing-answer-key, foreign-choice-marker). (docs/lint-codes.md:17-80)
  • Contradictions: Both complete examples in essay.md (lines 7-11 and 63-78) validate with mdq-py with no error or warning. (docs/question-types/essay.md:7-78)

Central risks

  • Essay looks like the simplest type, but most of its rules live in the corpus and in mdq-py, not in the text: the tag paragraph, the answer key section, its extent and its empty form.
  • The response of a rich text essay has no defined format, so two hosts can exchange the same answer as Markdown and as HTML.

high F5: The response format of a "text" essay is not defined

Location: docs/question-types/essay.md:47-50, docs/responses.md:38

"text" indicates that the response should be a rich text input, potentially
supporting markdown or other formatting.

Description: input: text asks for a rich text editor "potentially supporting markdown or other formatting", and docs/responses.md:38 says the essay response is "the text the student wrote". Neither document says what the response string holds for a rich text editor: Markdown source, HTML, or text with the formatting removed. input: code and input: plain have no such doubt.

Impact: Two hosts that exchange responses (an LMS, a grader, an exporter) can store the same answer as Markdown in one and as HTML in the other. A renderer cannot tell which it received, and raw HTML in a response is also an injection risk when the host renders it as Markdown.

Suggested fix: State in docs/responses.md and in Input that the response of every essay is a string, and that for input: text it is CommonMark source. A host whose editor produces HTML converts it before it stores the response. plain and code responses are verbatim text.

medium F3: The answer key section has no grammar, and its heading variants and extent are not specified

Location: docs/question-types/essay.md:59-61

It starts with an `H2` heading with the text `## [answer-key]`

Description: The answer key section is defined only in prose; essay.md has no rule for it, unlike the ## [extra] section of ordering (ordering.md:146: "##" ws "[" "extra" "]" nl+ content). The prose says both "an H2 heading" and "the text ## [answer-key]", so it does not settle these inputs: the setext H2 [answer-key] + --- (mdq-py accepts it as the answer key), ## [answer-key] (mdq-py accepts), ## [Answer-Key], ### [answer-key] and ## [answer-key] Notes (mdq-py rejects them as forbidden-block-element in the epilogue). The prose also does not say where the section ends or what blocks it may hold: mdq-py reads every block up to the end of the question, so a later ## Rubric heading and its list are inside answerKey. Inside an exam the end is the next === or --- block, which the text does not mention. The forbidden elements of question-base.md are not checked in the section either: mdq-py keeps an H1 and a second [essay] paragraph after the answer key as answer key text (answerKey: "Key.\n\n[essay]"), and prose after the answer key meant as epilogue goes into it. No example in examples/ has a heading, a bracketed paragraph or more prose after the answer key, or any heading form other than ## [answer-key].

Impact: Two implementations can split the same document into a different epilogue and answer key.

Suggested fix: Add a grammar rule, for example answer_key : "##" ws "[" "answer-key" "]" ws? nl md_block+. State that the heading is an ATX H2 alone on its line (decide on the setext form; CommonMark reads both as H2), and that the section holds every block after it, headings included except H1, up to the end of the question (end of file, or the next block in an exam).

medium F7: An empty or repeated answer key section has no documented rule

Location: docs/question-types/essay.md:92-95

| answerKey | error    | blank-text                   | if defined, must have at least one visible character       |

Description: The Additional Rules table has no rule for a second ## [answer-key] section, but examples/invalid/essay-two-answer-keys.mdq.md expects a parse-error. For a section with no content (## [answer-key] as the last line), the blank-text rule suggests an error, but mdq-py accepts the document and drops the field: the result has no answerKey and no error. The corpus already decides the empty case the other way: examples/valid/essay/empty-answer-key.mdq.md is valid and expects only missing-answer-key, while examples/invalid/model-only/essay-blank-answer-key.yaml is a blank-text error. So the rule that an empty Markdown section defines no answer key exists only in the corpus.

Impact: The corpus enforces a rule the spec does not state, and an empty section, which is almost always an unfinished question, passes with only the missing-answer-key info at most.

Suggested fix: Add a rule for a second section (parse-error) to the table. For the empty section, two readings are defensible: (a) an empty section is an absent answer key, reported only as missing-answer-key, as the corpus decides (examples/valid/essay/empty-answer-key.mdq.md); (b) it is a defined but blank field, blank-text, as for title: with only spaces. Recommended: (a), since ## [answer-key] with nothing after it is a common template placeholder, and state it in the text and the table.

medium F8: The text never maps the answer key section to the answerKey field

Location: docs/question-types/essay.md:53-78

## Answer key

Description: The Answer key section describes the Markdown syntax but never states that its content becomes the answerKey field of the AST, nor how the blocks are joined into the string. The field name appears only in the Additional Rules table (lines 92 and 95) and in schema/essay.yaml:41. The document also has no YAML form of a parsed essay.

Impact: A reader of the Markdown spec cannot tell which field holds the answer key, or that it is a field of the body and therefore invalid in the frontmatter (invalid-frontmatter-field).

Suggested fix: Add one sentence: the blocks of the section, without the heading, are the answerKey string, with the same normalization license as stem and epilogue. Add the YAML form of the example.

medium F9: The Grading section does not give the score range, automation or response

Location: docs/question-types/essay.md:80-82

Essay questions are graded manually.

Description: The rules that apply to an essay are spread over other documents: the automation is manual (question-base.md:280), every response is pending (responses.md:312-313), the score is in [0, 1] (exam.md:359), the exam grading does not apply (exam.md:359), and the response is a string (responses.md:190-204). The essay document links to none of them, and the instructor's score range is stated only for fill-in blanks (responses.md:320-321). ordering.md has Automation and Response sections; essay does not.

Suggested fix: Expand Grading: the automation is manual, every response is pending until the instructor gives a score in [0, 1], the exam grading does not apply and penalty does. Add a Response section that links to responses.md.

medium F25: Exam rules about --- and setext headings do not cover the essay answer key

Location: docs/exam.md:161-165

Inside an exam, the epilogue of a question MUST NOT use `---` as a thematic
break.

Description: The exam rules name only the epilogue (and the stem and instructions for setext-heading). The answer key comes after the epilogue and is the last block of an essay in an exam, so a --- in it has the same problem. mdq-py applies the epilogue rule to it: a --- in the answer key gives parse-error with the message "a question's epilogue cannot use '---'", and a setext [answer-key] heading gives setext-heading at path epilogue while it parses as answerKey. The spec does not state either behavior and no example in examples/ covers it.

Impact: Implementations can accept a --- in an answer key, and a later question then starts inside it.

Suggested fix: Extend the exam rules to every block after the body, the answer key included.

Exploitability conditions: An essay with an answer key inside an exam.

low F26: Essay spec does not say how footnotes resolve across the stem, epilogue and answer key

Location: docs/question-types/essay.md:59-61

The answer key section is placed below the `[essay]` tag and any existing

Description: Each part is stored as its own Markdown string. mdq-py accepts a stem with [^1] whose definition is in the answer key: the stem keeps a reference with no definition, and the definition is hidden with the answer key. The spec does not say if a footnote reference must be defined in the same field, and no example in examples/ covers it (examples/valid/essay/epilogue-starts-with-footnote.mdq.md only has an epilogue footnote).

Impact: The student view renders a dangling footnote, or a host that renders the whole document shows text from the answer key.

Suggested fix: State that a footnote definition belongs to the field it is in, and lint a reference defined in another field.

Exploitability conditions: An essay that uses footnotes and has an answer key.

Location: docs/question-types/essay.md:35

Mechanical fix

essay : "[essay]"

Description: The rule has no ws? before or after the tag. Tested with Lark: [essay], [essay], \t[essay] and [essay] are all rejected. But question-base.md:219-220 says "a tag may be indented", and grammar.md:59-69 defines the leading ws? of a block as the CommonMark indentation of at most three spaces. low F2: Essay grammar does not say it applies to a paragraph, so it accepts the content of a list item

Location: docs/question-types/essay.md:30-36

The body consists of a single `[essay]` tag.

Description: The grammar matches only the text [essay] and does not state the block that holds it. grammar.md:73-79 says a list-item grammar applies to the item content after the removal of the marker. With that reading, the content of * [essay] is [essay] and the grammar accepts it, while the Additional Rules table (essay.md:90) forbids the tag as a list item (foreign-choice-marker). The content of the heading ## [essay] is also [essay]. mdq-py reads only a paragraph as the tag: * [essay] gives foreign-choice-marker and ## [essay] gives a missing body. Impact: The block context of the tag comes from implementation behavior and a footnote, not from the grammar.

Suggested fix: State that the body is a paragraph whose only content is the rule, for example essay_block : ws? "[essay]" ws? nl, and that a list item or heading is not the tag. State that a later [essay] paragraph is a forbidden element of the epilogue, and list the parse errors in the Additional Rules table, as other types do.

low F4: SLUG accepts essay, so [essay] at the start of the first paragraph is a slug

# [Spec] Define the `[essay]` paragraph and the `## [answer-key]` section in the grammar

**Labels:** medium, low

## Problem

The essay grammar is one literal, and the answer key section has no grammar at all. What the tag paragraph is, how the answer key heading is spelled, where the section ends, what an empty or repeated section is, and which field it fills are known only from the corpus and mdq-py. Recommended: write `essay_block` and `answer_key` rules, state that the section runs to the end of the question and fills `answerKey`, document an empty section as an absent answer key (corpus behavior), a second section as `parse-error`, and that a footnote belongs to the field it is in. Decide whether a setext `[answer-key]` heading is valid (recommended: yes, as CommonMark reads it as H2) and whether type tag names can be slugs (recommended: yes, and a paragraph of only `[essay]` is always the tag).

## Evidence

- `docs/question-types/essay.md:30-36`: Essay grammar does not say it applies to a paragraph, so it accepts the content of a list item

  ```markdown
  The body consists of a single `[essay]` tag.
  ```
- `docs/question-types/essay.md:59-61`: The answer key section has no grammar, and its heading variants and extent are not specified

  ```markdown
  It starts with an `H2` heading with the text `## [answer-key]`
  ```
- `docs/question-types/essay.md:92-95`: An empty or repeated answer key section has no documented rule

  ```markdown
  | answerKey | error    | blank-text                   | if defined, must have at least one visible character       |
  ```
- `docs/question-types/essay.md:53-78`: The text never maps the answer key section to the `answerKey` field

  ```markdown
  ## Answer key
  ```
- `docs/question-types/question-base.md:194`: SLUG accepts `essay`, so `[essay]` at the start of the first paragraph is a slug

  ```lark
  SLUG: /[a-zA-Z0-9]+([-_][a-zA-Z0-9]+)*/
  ```
- `docs/question-types/essay.md:59-61`: Essay spec does not say how footnotes resolve across the stem, epilogue and answer key

  ```markdown
  The answer key section is placed below the `[essay]` tag and any existing
  ```

## Impact

- **Essay grammar does not say it applies to a paragraph, so it accepts the content of a list item:** The block context of the tag comes from implementation behavior and a footnote, not from the grammar.
- **The answer key section has no grammar, and its heading variants and extent are not specified:** Two implementations can split the same document into a different epilogue and answer key.
- **An empty or repeated answer key section has no documented rule:** The corpus enforces a rule the spec does not state, and an empty section, which is almost always an unfinished question, passes with only the `missing-answer-key` info at most.
- **The text never maps the answer key section to the `answerKey` field:** A reader of the Markdown spec cannot tell which field holds the answer key, or that it is a field of the body and therefore invalid in the frontmatter (`invalid-frontmatter-field`).
- **SLUG accepts `essay`, so `[essay]` at the start of the first paragraph is a slug:** Contrived inputs where the spec gives two readings of the same bracket.
- **Essay spec does not say how footnotes resolve across the stem, epilogue and answer key:** The student view renders a dangling footnote, or a host that renders the whole document shows text from the answer key.

## Suggested fix

- **Essay grammar does not say it applies to a paragraph, so it accepts the content of a list item:** State that the body is a paragraph whose only content is the rule, for example `essay_block : ws? "[essay]" ws? nl`, and that a list item or heading is not the tag. State that a later `[essay]` paragraph is a forbidden element of the epilogue, and list the parse errors in the Additional Rules table, as other types do.
- **The answer key section has no grammar, and its heading variants and extent are not specified:** Add a grammar rule, for example `answer_key : "##" ws "[" "answer-key" "]" ws? nl md_block+`. State that the heading is an ATX H2 alone on its line (decide on the setext form; CommonMark reads both as H2), and that the section holds every block after it, headings included except H1, up to the end of the question (end of file, or the next block in an exam).
- **An empty or repeated answer key section has no documented rule:** Add a rule for a second section (`parse-error`) to the table. For the empty section, two readings are defensible: (a) an empty section is an absent answer key, reported only as `missing-answer-key`, as the corpus decides (examples/valid/essay/empty-answer-key.mdq.md); (b) it is a defined but blank field, `blank-text`, as for `title:` with only spaces. Recommended: (a), since `## [answer-key]` with nothing after it is a common template placeholder, and state it in the text and the table.
- **The text never maps the answer key section to the `answerKey` field:** Add one sentence: the blocks of the section, without the heading, are the `answerKey` string, with the same normalization license as `stem` and `epilogue`. Add the YAML form of the example.
- **SLUG accepts `essay`, so `[essay]` at the start of the first paragraph is a slug:** State whether a type tag name such as `essay` can be a slug, and that a paragraph of only `[essay]` is always the essay tag.
- **Essay spec does not say how footnotes resolve across the stem, epilogue and answer key:** State that a footnote definition belongs to the field it is in, and lint a reference defined in another field.

- [ ] The Additional Rules table lists the second-section and tag-paragraph errors
- [ ] The corpus has examples for a section with headings inside and for the empty section

# [Spec] Define the response format of a "text" essay

**Labels:** high

## Problem

`input: text` is a rich text editor, but neither essay.md nor responses.md says whether the response string is Markdown, HTML or plain text. Options: (a) CommonMark source for `text`, verbatim text for `plain` and `code`; (b) leave it to the host. Recommended: (a), since MDQ is Markdown and a host with an HTML editor can convert.

## Evidence

- `docs/question-types/essay.md:47-50, docs/responses.md:38`: The response format of a "text" essay is not defined

  ```markdown
  "text" indicates that the response should be a rich text input, potentially
  supporting markdown or other formatting.
  ```

## Impact

Two hosts that exchange responses (an LMS, a grader, an exporter) can store the same answer as Markdown in one and as HTML in the other. A renderer cannot tell which it received, and raw HTML in a response is also an injection risk when the host renders it as Markdown.

## Suggested fix

State in `docs/responses.md` and in Input that the response of every essay is a string, and that for `input: text` it is CommonMark source. A host whose editor produces HTML converts it before it stores the response. `plain` and `code` responses are verbatim text.

## Acceptance criteria

- [ ] responses.md and essay.md state the format of the response for each `input`
- [ ] A corpus response example exists for an essay

# [Spec] Document essay grading, response and answer key visibility in essay.md

**Labels:** medium, low, info

## Problem

The essay Grading section is one sentence. The automation, the pending state, the [0, 1] score range, the exam `grading` exclusion and the response shape live in three other documents, and the text does not say when the answer key can be shown. Recommended: add Automation and Response sections as ordering has, and state that the answer key MUST NOT be shown before the student submits and MAY be shown after, even while pending. Also decide whether MDQ covers response length limits (recommended: no; state that they go in the stem or `meta`).

  key section is optional and serves as a guide for the instructor to grade the
