Methodology

The audit covered the short-answer question type: docs/question-types/short-answer.md, the shared references it depends on (docs/references/patterns.md, docs/references/grammar.md), docs/question-types/question-base.md, docs/exam.md, docs/responses.md, the short-answer blanks of docs/question-types/fill-in.md, schema/short-answer.yaml and the short-answer corpus in examples/.

scripts/spec_audit.py passed all 14 steps before the audit. The lead auditor read the specs and probed edge cases with the mdq-py parser. A grammar subagent turned the Lark snippets into test grammars and checked what they accept and reject against the prose and the corpus. An independent scanner subagent read the type specification, the schema and the corpus, validated every complete example with mdq validate, and checked the Additional Rules table against the MUST, SHOULD and MAY requirements of the text.

Spelling and grammar fixes were made in place and are not findings.

Strengths and weaknesses

Strengths

  • Grammar violations: The short-answer block grammar enforces the block-shape rules it covers. Tested with Lark. Accepted: [short-answer]: Brasília, [short-answer/accept]: Brasília, an exact literal with a trailing tab, an exact literal with inner spaces, an empty [short-answer]: with and without trailing ws, a list after the tag (LF, CR, CRLF, trailing ws before nl), [short-answer/reject]: Rio, a reject list, a bare * and inner backticks as inexact content. Rejected, as the rules require: an empty [short-answer/reject]:, accept and reject with a list after a blank line, content followed by a list, an unclosed backtick, [short-answer/accept/reject]: and [short-answer/preAccept]:. (docs/question-types/short-answer.md:149-160)
  • Grammar violations: The common ws/nl rules hold for short-answer: tab after the colon is ws; CR, LF and CRLF all end the tag line; U+00A0 after the colon is read as text (accepted as PLAIN_TEXT, as grammar.md:44-46 states); U+00A0 before the tag and a four-space indent are not accepted as a tag. EXACT_TEXT and PLAIN_TEXT use only explicit classes, as the regex dialect section requires. (docs/references/grammar.md:9-46)
  • Omissions: The grading rules of short answer are an ordered list with an explicit default for unmatched, and every branch (accept, reject, unmatched incorrect/manual, reject-only, no pattern) has a grading vector. (docs/question-types/short-answer.md:256-269, examples/grading/short-answer.yaml:96-163)
  • Ambiguities: The inexact comparison is a numbered list of steps over versioned Unicode/CLDR tables, with a worked table and per-step vectors for both diacritics values. (docs/references/patterns.md:43-99, examples/matching/inexact.yaml)
  • Contradictions: All nine complete markdown examples of short-answer.md, patterns.md and the fill-in short-answer blank section validate with mdq-py with no diagnostic, and the detached-list counterexample gets the documented detached-answer-list warning. (docs/question-types/short-answer.md:7-64, docs/question-types/short-answer.md:310-372, docs/references/patterns.md:25-29, docs/question-types/fill-in.md:244-254)
  • Omissions: The parse-error rows of Additional Rules (repeated block, content followed by a list, empty reject, interleaved feedback) and the regex flag rows each have an invalid corpus example with the expected code. (examples/invalid/short-answer-repeated-block.lint.json, examples/invalid/short-answer-content-and-list.lint.json, examples/invalid/short-answer-empty-reject.lint.json, examples/invalid/short-answer-interleaved-observations.lint.json, examples/invalid/short-answer-repeated-regex-flag.lint.json)

Central risks

  • The single-line form and the list form of a pattern block are specified in three places (prose, Lark snippet, patterns.md continuation rules) that disagree; mdq-py follows CommonMark, which none of them states.
  • Regex semantics (Unicode mode, case folding, shorthand classes, subject normalization) are left to the host regex engine, so mdq-py and mdq-js will grade the same response differently.
  • Several diagnostics exist only in the corpus and the implementation, not in the Additional Rules table, so the table cannot serve as the list of lint codes for short answer.

medium F14: responses.md says every short answer is case folded before matching

Location: docs/responses.md:156-158

Mechanical fix

Short answers are normalized before matching -- case folded, Unicode

Description: Only inexact literals are case folded and have their whitespace collapsed. Exact literals keep case and interior whitespace (patterns.md:133-134), and a regex is case-sensitive unless it has i (patterns.md:281).

Impact: A reader of responses.md expects ` math.isnan to accept Math.isnan`.

Suggested fix: Say that each pattern normalizes the response in its own way, with a link to patterns.md.

high F9: Single-line content: which lines continue the pattern is unclear

Location: docs/references/patterns.md:223-226, docs/question-types/short-answer.md:182-183

The content of a single-line block continues in the same way. The lines after
the tag line, up to the first blank line, continue the pattern:

Description: The text says every line after the tag line, up to the first blank line, continues the pattern. CommonMark lets a block quote, an ATX heading, a fenced code block, an HTML block or a thematic break interrupt a paragraph. mdq-py follows CommonMark: [short-answer]: Brasília followed by > Good gives accept: [Brasília] and epilogue: "> Good", and the same for ## Heading and <div>x</div>. Read literally, the spec makes the pattern Brasília > Good. For a list line the two texts contradict each other: by patterns.md, [short-answer]: Brasília followed by * Rio de Janeiro is the pattern Brasília * Rio de Janeiro, but short-answer.md:182-183 and row 414 make it a parse-error, as do mdq-py and examples/invalid/short-answer-content-and-list.mdq.md. A > line right after single-line content also looks like feedback, which short-answer.md:169-170 says the single-line form cannot have. A ! line is treated differently again: [short-answer]: Brasília followed by ! note gives the pattern Brasília ! note in mdq-py, so a comment silently changes the answer key. An empty tag followed by a text line ([short-answer]: then Brasília) gives accept: [Brasília] in mdq-py.

Impact: Two implementations can produce different answer keys from the same document. An author who writes feedback under a single-line answer gets it in the epilogue, shown to every student, with no diagnostic.

Suggested fix: State which lines end the single-line content: the same lines that LAZY_START excludes (grammar.md, Feedback and comment lines). Decide what a > or ! line right after single-line content is: an error, a warning, or feedback for that pattern.

Exploitability conditions: A single-line [short-answer]: block followed, without a blank line, by a line that starts a block quote, heading, fence, HTML block or thematic break.

high F11: Regex Unicode mode, case folding and shorthand classes are undefined

Location: docs/references/patterns.md:260-267, docs/references/patterns.md:304-305

* Unicode: Unicode characters are allowed in the regex. Unicode escape sequences

Description: The u flag is ignored, so it is not clear whether a regex runs in JavaScript Unicode mode. That decides if . matches one astral code point (/./ vs an emoji), if \u{1F600} is valid, and how i folds case (/s/i vs ſ, /k/i vs U+212A KELVIN SIGN). The spec says \d, \w, \s have JavaScript semantics; mdq-py compiles with Python re, where \d matches ٣ and \s differs as grammar.md:11-15 itself describes. 'users SHOULD NOT assume UTF-16 encoding' is advice to authors, not a rule for implementations.

Impact: The same regex accepts different responses in mdq-py and mdq-js.

Suggested fix: Pick one mode (recommended: code points, as JavaScript u/v mode and Python re do) and state the semantics of ., i (simple case folding?) and the shorthand classes (ASCII only, as JavaScript). Add vectors to examples/ for each.

Exploitability conditions: A regex with ., i, \d, \w or \s and a non-ASCII response.

medium F12: Regex delimiters: an unescaped / in the body and spaces after the flags

Location: docs/references/patterns.md:147-150, docs/references/patterns.md:31-32

A regex must be closed by a `/` as well, and may include optional flags after

Description: The text does not say which / closes the regex. patterns.md:31 implies the last one (/usr/bin is usr with flags bin), and mdq-py accepts /a/b/ as the body a/b, which is a syntax error in JavaScript. Leading spaces and tabs are stripped (line 147), but trailing ones are not: mdq-py rejects the item * /abc/i with 'unknown regex flag: " "', while an exact literal allows them (EXACT rule ws?).

Impact: Authors cannot predict whether / needs escaping; implementations that follow JavaScript literal syntax reject documents mdq-py accepts.

Suggested fix: State that the last / closes the regex and that an unescaped / in the body is allowed (or forbidden, invalid-regex). State that spaces and tabs after the flags are stripped.

medium F13: The n flag strips diacritics from the regex source with no rule for escapes

Location: docs/references/patterns.md:289-294

* `n`: Strip diacritics from both the pattern and the response before

Description: Stripping diacritics from a regex source is not the same as from text. mdq-py normalizes only the literal characters written in the source: /caf\u00e9/n keeps é in the compiled regex and so never matches the stripped response cafe. A class such as [\u0300-\u036f] or a literal combining mark inside a class changes meaning after the strip. The spec says nothing about either case.

Impact: A regex with n can match nothing, with no diagnostic, and implementations can differ.

Suggested fix: Define n on the subject only (strip the response) and require the regex to be written without diacritics, or define how escapes are treated. A lint for a regex under n that still holds an Mn code point would catch the mistake.

medium F25: Pattern feedback is said to come from the pattern that 'decided' the response, but the rule picks the first matching pattern that has feedback

Location: docs/references/patterns.md:166-167, schema/short-answer.yaml:108, docs/question-types/short-answer.md:388-392

Only `pattern` is required. `feedback` is shown to the student whose response

Description: patterns.md and the schema say feedback is shown to the student whose response the pattern decided. short-answer.md:391-392 says the student gets the feedback of the FIRST pattern that matches AND defines a feedback message. With accept: ["/cerrad[oa]/i", {pattern: Cerrado, feedback: Right}], the response Cerrado is decided by the first pattern, which has no feedback; by short-answer.md it shows Right, by patterns.md it shows nothing. 'Decided' is not defined for a response that several patterns match.

Impact: Implementations can show or omit feedback for the same response.

Suggested fix: In patterns.md and the schema, refer to the selection rule of short-answer.md ('Feedback') instead of 'the pattern that decided'.

Exploitability conditions: A response that matches two patterns of the deciding list, and only the later one has feedback.

high F10: The response is not normalized or trimmed before a regex match

Location: docs/references/patterns.md:145-150

A pattern is a regex if it starts with a `/` after stripping spaces and tabs.

Description: Exact literals define NFC plus trimming (patterns.md:126-131) and inexact literals define six steps, but no text says what happens to the response before a regex matches it. The implicit anchors make this visible: does /1822-0?9-0?7/ accept 1822-09-07 (leading space) or 1822-09-07\n? Does /Brasília/ accept Brasília typed in NFD? mdq-py matches the raw response, so both fail. examples/grading/short-answer.yaml tests trimming only for literals.

Impact: A student who types a trailing space or newline, or whose input method produces NFD, fails a regex answer that a literal would accept. Implementations can disagree.

Suggested fix: Define the regex subject, for example: normalize the response to NFC and remove UNICODE_SPACE from both ends, as for exact literals. Add grading vectors for it.

Exploitability conditions: Any regex pattern, with a response that has surrounding whitespace or is not in NFC.

medium F15: Short-answer response: type, empty string and line breaks are not defined

Location: docs/responses.md:148-153

The text the student wrote, before normalization.

Description: The section does not say that a value that is not a string (1960, a list, a mapping) is a malformed response, as numeric and true/false do. It does not say how an empty string or a string of only spaces is graded: it is not null, so it is not skipped; examples/grading/short-answer.yaml grades "" as pending only for a manual question. It does not say if the text can hold line breaks; inexact step 6 collapses them, a regex . never matches one.

Impact: A YAML response 1960 can be coerced to text in one implementation and refused in another. An empty submission scores 0 under unmatched: incorrect but its status is not specified.

Suggested fix: Add: the response is a string; any other value is a malformed response (ResponseError). State that an empty or whitespace-only string is graded like any other response (or is a skip). Add vectors.

medium F16: The required [short-answer] tag has no rule row and blocks the frontmatter-only form

Location: docs/question-types/short-answer.md:140-145, docs/question-types/short-answer.md:204-206

incorrect responses. A question MUST have a `[short-answer]` block and MAY

Description: The MUST has no row in Additional Rules and no lint code. mdq-py rejects a .mdq.md with type: short-answer and accept in the frontmatter and no tag ('parse-error: A required field is missing'). The author must write an empty [short-answer]: tag, which line 204 implies is allowed with an accept field but never states. The frontmatter field is called 'the canonical form' (short-answer.md:91), yet it cannot stand alone in markdown.

Impact: Authors who use the frontmatter form get an unexplained parse error, and the empty tag that fixes it looks like a 'no pattern' question.

Suggested fix: Either drop the requirement when type or accept/reject is in the frontmatter, or keep it and add a row (parse-error) plus a sentence that an empty tag with an accept field is valid.

medium F17: Additional Rules misses the pattern-string and preAccept-block rules

Location: docs/question-types/short-answer.md:407-422

| accept, reject, preAccept, preReject | error    | schema-error           | a pattern list, when present, has at least one pattern (schema)                     |

Description: Rules stated in prose or enforced by the corpus have no row: a pattern string cannot be empty or blank (patterns.md:20; examples/invalid/short-answer-empty-pattern gives schema-error); content that opens with a backtick MUST be a complete span (short-answer.md:215-217; short-answer-partial-backtick gives schema-error); an empty pattern line in a list (short-answer-empty-pattern-line gives parse-error); a [short-answer/preAccept] block (short-answer-pre-accept-block gives forbidden-block-element, which the footnote at short-answer.md:104 does not mention). patterns.md:231 'Authors SHOULD write those on one line' has no warning code either.

Impact: The table is not the complete list of diagnostics; an implementer reading it misses four errors.

medium F18: An exact literal cannot contain a backtick

Location: docs/question-types/short-answer.md:158

EXACT_TEXT   : /[^`\n\r]+/

Description: EXACT_TEXT excludes the backtick and no escape exists, so an exact answer such as the shell command substitution ` date or the Markdown code cannot be written. CommonMark solves this with longer backtick fences ( ab` ). mdq-py gives a schema-error with the raw JSON Schema regex for ` x ``.

Impact: Questions about shells, Markdown or SQL identifiers cannot use exact matching; the error message does not help.

Suggested fix: Accept a CommonMark code span of N backticks, with the same one-space stripping, or document the limitation and suggest a regex.

medium F26: Feedback of preAccept and preReject patterns has no rule

Location: docs/question-types/short-answer.md:104-115, docs/question-types/fill-in.md:57-60

systems should warn students about the invalidity of their answer before

Description: The pattern object form allows feedback in every pattern list, and fill-in.md:57-60 shows a preReject entry with the feedback 'Write the season, not a month number.' The Feedback section (short-answer.md:386-403) covers only accept and reject. No text says when a pre-validation feedback is shown, which one when several patterns match, or what a student sees when no preAccept pattern matches. The lowercase 'should warn' at line 107 is also not an RFC 2119 keyword, so the level of the requirement is unclear.

Impact: Authors write pre-validation feedback that implementations may never show, or show differently.

Suggested fix: Add a rule: when a submission is invalid, show the feedback of the first matching preReject pattern that has one; state what is shown for a preAccept failure (no pattern matched, so no pattern feedback). Write the warning requirement with SHOULD.

Exploitability conditions: A preAccept or preReject entry with feedback.

medium F27: Short answer blanks of fill-in have no incorrectFeedback, and the spec does not say so
