Methodology

Read docs/references/grammar.md, docs/references/patterns.md, docs/question-types/question-base.md, docs/exam.md, docs/responses.md, docs/references/choices.md and docs/question-types/true-false.md, and checked suspicious rules against the corpus (examples/valid/true-false/, examples/invalid/true-false-*, examples/grading/true-false.yaml) and the reference implementation (mdq-py, mdq validate).

A second subagent scanned true-false.md independently: prose against the Additional Rules table (MUST/SHOULD/MAY against error/warning/info), against schema/true-false.yaml, docs/lint-codes.md and the corpus, and validated the complete example with mdq-py. scripts/spec_audit.py passed before and after the audit.

Strengths and weaknesses

Strengths

  • Omissions: The marker/correct split is well argued: correct drives grading, marker keeps round-tripping and enables the WARNING and locale lints, and the spec says which lints are lost without marker. (docs/question-types/true-false.md:107-144)
  • Contradictions: The symmetric and partial rows of the grading table agree with the prose and with examples/grading/true-false.yaml, including abstentions and explicit-null cases. (docs/question-types/true-false.md:213-225)
  • Omissions: The corpus covers every true/false lint code in the Additional Rules table, including CJK, non-BMP, non-NFC, false-friend lowercase and locale without expectation (examples/valid/true-false/). (docs/question-types/true-false.md:228-252)
  • Inconsistencies: Feedback rules for true/false (wrong and abstained statements, document order, none on skip) agree with GLOSSARY.md Feedback and docs/responses.md Skipping. (docs/question-types/true-false.md:177-189)
  • Grammar violations: The true-false value rule, with true : /[TtVvSsU+5BF9U+771F]/, false : /[FfU+9519U+507D]/ and the WARNING class built from General_Category, accepts [T], [t], [V], [S], [F], [f], [U+5BF9], [U+771F], [U+9519], [U+507D], [ T ], [\tT\t], [é] (U+00E9) and the astral letter U+20000, and rejects [X], [x], [TF], [ ], [], [✓], [×], [U+3007], [1], [*] and [e\u0301], as the prose states (Lark Earley test). (docs/question-types/true-false.md:43-98)
  • Grammar violations: ws is only space and tab, so [\u00a0T] and [\u3000F] fail the value rule, which agrees with the rule that a Unicode space where the grammar expects ws is text. (docs/references/grammar.md:28-42)
  • Grammar violations: VALUE_END refuses a bracket followed by ( or [: * [T](http://x) a and * [T][a] a fail the item rule and stay links, in line with CHOICE_MARK and CHOICE_ID. (docs/references/choices.md:15-23, docs/references/choices.md:56-57)
  • Grammar violations: The item grammar is ambiguous about the ws after the value and about whether [brasilia] is a CHOICE_ID or text (2 and 4 parse trees in the Earley test), but the prose settles both: the bracket that matches CHOICE_ID is always the id, and the text excludes the ws after the value and the id. * [T] [brasilia] gives an empty text and * [T] [V] text gives the id V. (docs/references/choices.md:68-70, docs/references/choices.md:109-111)
  • Grammar violations: Feedback and comment rules hold for true-false items in the test: > fb then ! c is accepted, a lazy line continues the feedback, a blank line before the feedback is accepted, an empty > line is part of the block, ![x](y.png) is a lazy line and not a comment, 2. two is a lazy line and 1. one is not, and a second > block after a comment fails the rule (the stated parse-error). (docs/references/grammar.md:116-161)
  • Grammar violations: Type inference decides mixed lists: [x] with [T] is multiple selection by rule 2 and [T] is a foreign-choice-marker; [ ] with [F] is true/false by rule 3 and [ ] is a foreign-choice-marker (as examples/invalid/true-false-blank-marker expects); [✓]/[✗] falls to rule 4. The X/x exclusion of the WARNING set matches rule 2, so no letter is claimed by both types. (docs/question-types/question-base.md:229-245, docs/question-types/true-false.md:85)
  • Grammar violations: No compatibility ideograph whose NFC form is a TRUE or FALSE letter changes the meaning: the only ones found, U+2F946 and U+2F947 (NFC U+771F), are WARNING letters and so also mean true (scan of all \p{L} code points with unicodedata, Unicode 15.1). (docs/question-types/true-false.md:83-86)
  • Schema mismatches: The true/false schema agrees with the spec on minItems: 2, the slug pattern of id, the grading enum, shuffle as boolean or inherit, correct required and additionalProperties: false on statements. (schema/true-false.yaml:17-111)
  • Contradictions: The only complete true/false document in the spec (the Example section) validates with mdq-py with no warning. (docs/question-types/true-false.md:9-16)

Central risks

  • The letter test of true/false depends on the Unicode database and the case mapping of each runtime, so Python and JavaScript can disagree on the type and the answer key of the same document.
  • The same strategy name (all-or-nothing) means different things in true/false and in the other types, so an exam-wide grading gives inconsistent results.

high F1: True/false all-or-nothing gives partial credit

Location: docs/question-types/true-false.md:204-207

* **all-or-nothing**: The student must mark all choices with the correct marking
  or abstain. Any mistake in the marked choices gives zero points. If all marked
  choices are correct, the student gets a score proportional to the number of
  correct markings (`correctly marked / total number of choices`).

Description: Under true/false all-or-nothing, a response with no mistakes scores correctly marked / total, so [T, F, _, _] scores 0.5 (table at line 223, and examples/grading/true-false.yaml:45-46). GLOSSARY.md defines All-or-nothing as 'scoring 1 only when every part is correct, and 0 otherwise', and multiple selection (docs/question-types/multiple-selection.md:114-115) and fill-in (docs/question-types/fill-in.md:327) follow the glossary. The true/false rule is 'partial, unless there is a mistake'.

Impact: An exam that sets grading: all-or-nothing for every type gets two different meanings. An instructor who expects no credit for an incomplete true/false answer gives 0.5 to a student who judged half of the statements.

Suggested fix: Either make true/false all-or-nothing score 1 only when every statement is judged correctly (an abstention counts as a mistake), or keep the current rule, give it a different name, and update the glossary. The first option agrees with the glossary and the other types.

medium F32: docs/lint-codes.md makes a null feedback or comment a schema-error

Location: docs/lint-codes.md:72, docs/question-types/question-base.md:103-107

Mechanical fix

`null` in these fields is a `schema-error`.

Description: The blank-text row lists the feedback and comment of a choice, which are OPTIONAL, and ends with 'null in these fields is a schema-error'. question-base.md:103-107 says a null in any OPTIONAL field, including nested objects such as choices, is the same as an absent field, and question-base.md:349 repeats it. mdq-py accepts a true/false statement with feedback: null.

Impact: An implementation that follows docs/lint-codes.md rejects feedback: null, which the base spec and the reference implementation accept.

Suggested fix: Change the sentence to: 'null in an OPTIONAL field is an absent field; in a required field it is a schema-error.'

Exploitability conditions: A YAML or JSON document with feedback: null or comment: null on a choice.

medium F3: The spec does not define which markers are locale-mismatched

Location: docs/question-types/true-false.md:149-153

Implementations MAY issue warnings for True/False letters that are incompatible
with the locale for the question. For instance, if `locale: pt-BR`, it may
expect `V` and `F` -- for "verdadeiro" (true) and "falso" (false) -- and could
issue a warning if `T` is used instead.

Description: 'Incompatible with the locale' is defined only by one example (T under pt). Open cases: is S, U+5BF9 or U+9519 under pt mismatched? Is a WARNING letter such as W under pt also mismatched, or only unlisted-true-false-marker? Is lowercase t mismatched (case-insensitive)? mdq-py warns for every TRUE or FALSE letter outside the expected pair, case-insensitively, and never for a WARNING letter: under pt-BR it flags S, t, U+5BF9, U+9519 and not W.

Impact: Two implementations can report different warnings for the same document.

Suggested fix: State the rule: under a locale in the table, a marker in the TRUE or FALSE category whose case-folded form is not the expected letter of its category is mismatched. WARNING letters get only unlisted-true-false-marker.

Exploitability conditions: locale with a language subtag in the table.

medium F5: NFC rule mixes combining sequences with non-NFC single code points

Location: docs/question-types/true-false.md:65-68, docs/question-types/true-false.md:251

* "One code point", not one grapheme cluster. A base letter followed by a
  combining mark is two code points and is not a valid marker. Implementations
  MAY report, at the info level, a marker that is not in NFC form: in NFC,
  precomposed forms are single code points.

Description: The bullet says a combining sequence is invalid (an error), then in the same breath offers an info for a marker 'not in NFC form', with the reason 'in NFC, precomposed forms are single code points'. That reason is about combining sequences, which are already malformed-true-false-marker. The info can only apply to a single code point whose NFC form differs, such as U+212B ANGSTROM SIGN (NFC U+00C5) or U+212A KELVIN SIGN (NFC K), which is the case examples/valid/true-false/non-nfc-marker.yaml tests and docs/lint-codes.md:39 describes. The table row 'is not a single code point in NFC form' can be read as covering combining sequences too.

Impact: An implementer can emit the info for combining sequences, or miss the singleton case.

Suggested fix: Split the bullet: a combining sequence is two code points and is malformed-true-false-marker; a single code point that NFC changes (U+212B to U+00C5) MAY get non-nfc-true-false-marker. Reword the table row to 'is a single code point that NFC changes'.

medium F6: Case-insensitivity and compatibility forms of letters are not defined

Location: docs/question-types/true-false.md:46-50, docs/question-types/true-false.md:83-86, docs/question-types/true-false.md:96-98

We only show the upper case versions of each symbol. Each set must be expanded
with lowercase versions as well; the CJK characters have no case and are used
as-is.

Description: The spec does not say which case mapping applies. mdq-py uses case folding: [ſ] (U+017F LATIN SMALL LETTER LONG S) folds to s and reads as TRUE with no warning. The fullwidth letters that CJK input methods produce are WARNING letters: [U+FF26] (U+FF26) reads as true with only unlisted-true-false-marker, so a statement the author marked false is graded as true. A titlecase letter (Lt, such as U+01C5) is a WARNING letter too.

Impact: Implementations that use lowercase mapping, case folding or NFKC give different categories for the same marker. The fullwidth U+FF26 case flips the answer key with only a warning.

Suggested fix: Define the comparison: for example, NFKC then case folding before the category lookup, so U+FF26 is FALSE and ſ is TRUE. Or keep exact comparison of the letter and its simple lowercase, and make a fullwidth U+FF34/U+FF26 an error. Add corpus examples for the chosen rule.

medium F27: marker is 'exactly as it was written', but the ws inside the brackets is dropped

Location: docs/question-types/true-false.md:113, docs/question-types/true-false.md:137-139

| marker  | string  | The letter itself, exactly as it was written.           |

Description: The value rule allows ws around the letter ([ T ], [F ], [\tT\t]), and examples/valid/true-false/spaced-markers.yaml stores marker: T for each. The spec says marker is the letter 'exactly as it was written' and 'stored verbatim', and that it keeps the ability 'to be written back out unchanged' (line 142-143). It does not say that the spaces are removed, nor that spacing is lost on a round trip.

Impact: An implementation that reads 'verbatim' literally stores T , which then fails malformed-true-false-marker and the schema maxLength: 1.

Suggested fix: Say that marker is the letter of the value without the ws around it, and that only the letter and its case are kept.

low F10: False-friend footnote speaks of an S 'meaning false'

Mechanical fix

low F12: Type inference 'a value is a letter' does not say spaces are removed

Location: docs/question-types/question-base.md:230-234

3. a value is a letter: true/false;

Description: The true/false value rule allows ws around the letter ([ T ]), and examples/valid/true-false/spaced-markers.mdq.md infers true/false from such markers. Rule 3 says 'a value is a letter', and the value of [ T ] is T . 'letter' also does not link to its definition in true-false.md (one code point in \p{L}).

low F35: The introduction calls true statements 'correct answers'

Location: docs/question-types/true-false.md:5-7

Mechanical fix

rendition of a True or False marker. The correct answers are usually marked with
`[T]` and incorrect ones are usually marked with an `[F]`.

Description: In a true/false question every statement has a correct answer: [F] marks a false statement, and the correct answer for it is 'false'. 'Incorrect ones' suggests that [F] items are wrong answers, as [ ] items are in multiple choice. The Choices section uses the right terms ('true if the statement is true').

Impact: A reader can confuse the verdict of a statement with the correctness of a student's judgement, which the grading rules depend on.

Suggested fix: 'True statements are usually marked with [T] and false statements with [F].'

low F37: S is called the initial of words written in non-Latin scripts

Location: docs/question-types/true-false.md:87-88

Mechanical fix

`S` was chosen for TRUE over FALSE deliberately: it is the initial letter for
"true" in Hindi, Bengali, Arabic, Urdu and Japanese

Description: The cited words are in Devanagari, Bengali, Arabic, Urdu and Han script; S is the initial of their romanizations (satya, sahih, sach, shin), from the ascii column of the annex. The text does not say so. For Japanese, U+771F itself is already a TRUE letter.

Suggested fix: 'it is the initial of the romanized word for "true" in Hindi, Bengali, Arabic, Urdu and Japanese (satya, satya, sahih, sach, shin)'.

medium F7: Responses do not say that a null statement value is an abstention

Location: docs/responses.md:78-91

A mapping from statement id to the judgement the student made. Unlike multiple
selection, an absent key is **not** a false: it is an abstention, and the
student may deliberately leave a statement unjudged.

Description: The response is 'a mapping of statement id to boolean' (line 29), and only an absent key is an abstention. examples/grading/true-false.yaml:15-16 and its 'Explicit null' cases (line 68) treat earth-is-flat: null as an abstention too. The spec does not say whether null is an abstention or a malformed response, nor what a non-boolean value ("T", 1) is.

Impact: An implementation that follows the spec text rejects a response that the shared grading corpus requires it to accept.

Suggested fix: In docs/responses.md, say that a null value is the same as an absent key, and that any other non-boolean value is a malformed response. Do the same for multiple selection if null is allowed there.

medium F26: The marker/correct agreement rule and the reserved X rule exist only in the table

Location: docs/question-types/true-false.md:237-238, docs/question-types/true-false.md:107-144

| choices[].marker   | error    | reserved-true-false-marker               | must not be `X` or `x`[^2]                                 |
| choices[].marker   | error    | true-false-marker-disagrees-with-correct | must agree with `correct` according to its category[^3]    |

medium F28: The schema and malformed-true-false-marker both reject a marker that is not one code point

Location: docs/question-types/true-false.md:236, schema/true-false.yaml:94-95, docs/lint-codes.md:84

  ```markdown
  | choices[].marker   | error    | reserved-true-false-marker               | must not be `X` or `x`[^2]                                 |
  ```
- `docs/question-types/true-false.md:237-238, docs/question-types/true-false.md:107-144`: The `marker`/`correct` agreement rule and the reserved `X` rule exist only in the table

  ```markdown
  | choices[].marker   | error    | reserved-true-false-marker               | must not be `X` or `x`[^2]                                 |
  | choices[].marker   | error    | true-false-marker-disagrees-with-correct | must agree with `correct` according to its category[^3]    |
  ```
- `docs/question-types/true-false.md:113, docs/question-types/true-false.md:137-139`: `marker` is 'exactly as it was written', but the `ws` inside the brackets is dropped

  ```markdown
  | marker  | string  | The letter itself, exactly as it was written.           |
  ```
- `docs/question-types/true-false.md:236, schema/true-false.yaml:94-95, docs/lint-codes.md:84`: The schema and `malformed-true-false-marker` both reject a marker that is not one code point

  ```markdown
  | choices[].marker   | error    | malformed-true-false-marker              | must be a single letter[^2]                                |
  ```
- `schema/true-false.yaml:86-95`: Schema accepts any single code point as `marker`

  ```yaml
        marker:
          type: string
  ```
- `docs/question-types/true-false.md:141-144`: No rule for the letter to write when `marker` is absent

  ```markdown
  `marker` is OPTIONAL. A document carrying only `correct` is well-formed and
  grades identically; it has simply lost the ability to be written back out
  unchanged,
  ```

## Impact

- **Two error codes apply to `[x]` and `[TF]` in a list forced to true/false:** Implementations can report different codes for the same markdown input.
- **The `marker`/`correct` agreement rule and the reserved `X` rule exist only in the table:** A reader of the prose cannot know that a YAML document with `marker: F, correct: true` or `marker: X` is invalid, nor that a WARNING letter forces `correct: true`.
- **`marker` is 'exactly as it was written', but the `ws` inside the brackets is dropped:** An implementation that reads 'verbatim' literally stores ` T `, which then fails `malformed-true-false-marker` and the schema `maxLength: 1`.
- **The schema and `malformed-true-false-marker` both reject a marker that is not one code point:** An implementation that reports schema errors as `schema-error` fails the corpus for these documents, or reports two errors for one defect.
- **Schema accepts any single code point as `marker`:** A consumer that relies on the schema alone accepts markers the spec forbids.
- **No rule for the letter to write when `marker` is absent:** Two writers produce different markdown for the same document.

## Suggested fix

- **Two error codes apply to `[x]` and `[TF]` in a list forced to true/false:** Say in the table that `malformed-true-false-marker` and `reserved-true-false-marker` apply to the `marker` field of model input, and that a markdown value outside the `value` rule is `foreign-choice-marker`.
- **The `marker`/`correct` agreement rule and the reserved `X` rule exist only in the table:** Under Choices, add: 'When `marker` is present, its category MUST agree with `correct`: FALSE letters with `false`, TRUE and WARNING letters with `true` (`true-false-marker-disagrees-with-correct`). `marker` MUST NOT be `X` or `x` (`reserved-true-false-marker`).'
- **`marker` is 'exactly as it was written', but the `ws` inside the brackets is dropped:** Say that `marker` is the letter of the value without the `ws` around it, and that only the letter and its case are kept.
- **The schema and `malformed-true-false-marker` both reject a marker that is not one code point:** Either remove `minLength`/`maxLength` from the schema and leave the check to `malformed-true-false-marker`, or state that a dedicated code replaces `schema-error` when both apply to the same field.
- **Schema accepts any single code point as `marker`:** Add `pattern: "^\\p{L}$"` and `not: {enum: [X, x]}`, or say in the description that the letter and reserved checks are model rules (`malformed-true-false-marker`, `reserved-true-false-marker`). The first option interacts with the code-precedence question of the length check.
- **No rule for the letter to write when `marker` is absent:** State a default: 'A writer that needs a letter for a statement without `marker` SHOULD use the letters of the question's locale from the Locale table, and `T`/`F` otherwise.'

- [ ] Each marker rule is in prose and table with one code per case
- [ ] The schema description lists the model rules
