Strengths and weaknesses

Strengths

  • Grammar violations: Ordering grammar places sections strictly after the epilogue and rejects prose after a section. Tested with Lark (Earley) and stubs: epilogue then ## [extra] ACCEPTED; prose after the last section REJECTED; prose between ## [extra] and ## [reject] REJECTED; examples/invalid/ordering-epilogue-after-section.mdq.md and ordering-prose-between-sections.mdq.md REJECTED; examples/valid/ordering/epilogue.mdq.md ACCEPTED. This matches the prose at ordering.md:175-182 and the Additional Rules row at line 340. (docs/question-types/ordering.md:141-148)
  • Grammar violations: Ordering accept/reject sections with the shared observations rule enforce at most one feedback and one comment block, in either order, and no observations on [extra]. Tested: comment lines then blank then code ACCEPTED; > then ! with no blank ACCEPTED; feedback with a lazy line ACCEPTED; >/!/> interleaved REJECTED; two feedback blocks split by a blank line REJECTED; feedback under ## [extra] REJECTED; heading with observations and no content REJECTED; examples/invalid/ordering-interleaved-observations and ordering-two-feedback-blocks REJECTED, examples/valid/ordering/observations-adjacent ACCEPTED. (docs/question-types/ordering.md:146-148)
  • Grammar violations: Ordering tag and heading tokens hold for the stated literals: [ordering] with a code block or a ul list ACCEPTED (also with CRLF, tilde fences, - and + bullets); [ordering] with no block, [ ordering ], [Ordering], [ordering] sort these, ### [extra] and ##[extra] REJECTED; ##<TAB>[extra] ACCEPTED. Valid corpus bodies brazil-timeline, fibonacci, extra-text, list-markers ACCEPTED. (docs/question-types/ordering.md:141-148)
  • Inconsistencies: The epilogue and section order rule (sections after the epilogue, prose after a section is parse-error) matches question-base.md#epilogue and has invalid examples for both prose between sections and an epilogue after a section. (docs/question-types/ordering.md:175-182, docs/question-types/question-base.md:264-268, examples/invalid/ordering-prose-between-sections.mdq.md, examples/invalid/ordering-epilogue-after-section.mdq.md)
  • Omissions: Both complete Markdown examples in ordering.md validate with no error or warning in mdq-py. (docs/question-types/ordering.md:16-29, docs/question-types/ordering.md:34-89)
  • Schema mismatches: schema/ordering.yaml agrees with the spec on line shape ([level >= 0, text], exactly 2 items), lines minItems 2, unique normalizations, the indentation and unmatched enums and defaults, and the descriptions of lenient implying dedent. (schema/ordering.yaml:17-108, schema/ordering.yaml:138-156)
  • Ambiguities: Indentation unit inference (GCD of indented lines across all blocks, tab = 4 spaces, default 4) is precise and exercised by examples for GCD, tabs, cross-section units and lenient alignment. (docs/question-types/ordering.md:239-250, examples/valid/ordering/indentation-gcd.mdq.md, examples/valid/ordering/tab-indentation.mdq.md, examples/valid/ordering/indentation-unit-across-sections.mdq.md)
  • Contradictions: Grading, automation and pending status agree across ordering.md, question-base.md#automation and responses.md#pending: unmatched: manual gives semi-automatic and a pending response with no feedback; binary score with no partial credit. (docs/question-types/ordering.md:302-317, docs/question-types/question-base.md:283-285, docs/responses.md:316-322)

Central risks

  • The relations between the answer key, ## [extra], ## [accept] and ## [reject] (overlap, reachability, distractors in correct answers) are only partly stated, so a valid document can grade one response as both correct and incorrect.
  • The ordering grammar is stricter than CommonMark and mdq-py in several places (blank lines, indentation, heading variants), so a second implementation that follows it literally rejects the spec's own full example.

Location: docs/question-types/ordering.md:134-136, docs/question-types/ordering.md:106-108

low F14: Feedback is unspecified when a response matches more than one section

Location: docs/question-types/ordering.md:274-276

A response that matches an accepted or a rejected answer shows that section's
feedback, if it declares one. The `[ordering]` block itself carries no

Description: Two ## [accept] sections with the same normalized lines, or an ## [accept] equal to the [ordering] block, are only warnings (duplicate-alternative-lines, accept-repeats-answer-key), so valid documents exist where one response matches several sections with different feedback. Location: docs/question-types/ordering.md:225-229

medium F7: Nested ul items: how a text line gets an indentation level is not specified

Location: docs/question-types/ordering.md:159-162, docs/question-types/ordering.md:239-244

An item is exactly one line: an item with a continuation line or a second
paragraph is an error (`parse-error`), whatever the rendered markdown shows.

Description: The Indentation section measures the leading whitespace of each line, which is clear for a fenced code block. For a ul list the spec never says which whitespace counts: the list marker's indentation, a nested sub-list, or the content offset. A nested list (- a\n - b\n- c) is neither a continuation line nor a second paragraph, so line 161 does not cover it. mdq-py turns b into a separate line at level 1 (unit 2); no corpus example has an indented ul item.

Impact: Text questions with indentation (outlines, nested steps) have no defined parse; a second implementation may reject nested lists or flatten them.

Suggested fix: Decide: either nested list items are separate lines whose level comes from nesting depth (or marker column), or any nested list is a parse-error. State it in Body and Indentation and add valid/invalid corpus examples.

medium F9: Which responses are malformed versus wrong is not defined for ordering

Location: docs/responses.md:267-276

matched as many times as it appears. A response may hold a distractor from the
question's `extra` lines -- that is a wrong answer, not a malformed response.

Description: Only distractors are classified. The spec does not say whether these are ResponseError or just unmatched: a line whose text is neither in lines nor in extra; more copies of a line than the question presents; a level different from the authored one under indentation: fixed (the student cannot change it); an empty list; a response that leaves out some lines. medium F10: Initial indentation shown to the student under lenient and strict is not specified

Location: docs/question-types/ordering.md:230-234

* `"lenient"`: the student may change indentation freely, but it is ignored
  when grading. This implies the `dedent` normalization, whether or not
  `normalizations` lists it.
* `"strict"`: the student may change indentation, and it is compared like the
  rest of the line.

Description: Only fixed says lines are presented with their authored indentation. Under strict the spec does not say whether the shuffled lines start at their authored level (which gives away part of the answer the student is graded on) or flattened at level 0. Duplicates are defined as same text and same level (line 170), so whether two lines that differ only by level are shown as identical copies under strict also depends on this.

Impact: Hosts present the same strict question with different difficulty.

Suggested fix: State that under lenient and strict the lines are presented at level 0 (recommended for strict, since indentation is part of the answer), or at the authored level, and add it to the Indentation section.

high F1: Ordering grammar rejects blank lines between sections, including the spec's own full example

Location: docs/question-types/ordering.md:141

Mechanical fix

ordering : "[" "ordering" "]" nl content epilogue? section*

Description: section* puts each section heading right after the content block of the previous section. No blank_line is allowed between them, and the content block (a CommonMark fenced code block or list) does not include the blank lines that follow it. Tested with Lark (Earley) and stubs for md_code_block, md_ul and epilogue: the body of the full example at docs/question-types/ordering.md:45-88 is REJECTED at the blank line 60, before ## [accept]. The minimal input [ordering] / fenced block / ## [extra] / fenced block / blank line / ## [accept] / fenced block is also rejected. The blank line between the main content block and the first section is accepted only if the epilogue stub absorbs blank lines, which makes an epilogue of only blank lines. mdq-py accepts all these inputs.

Impact: The grammar contradicts the normal layout of every multi-section ordering question, including the one the spec shows. A reader or implementer who follows the grammar literally rejects valid documents.

Suggested fix: Allow blank lines before each section, for example ordering : "[" "ordering" "]" nl content epilogue? (blank_line* section)*. With this change the full example parses, and prose after a section is still rejected.

medium F2: Ordering tag rule has no ws? around [ordering], unlike other tags and the CommonMark paragraph

Location: docs/question-types/ordering.md:141

ordering : "[" "ordering" "]" nl content epilogue? section*

Description: The tag line has no ws? before [ or after ]. The grammar REJECTS [ordering] (up to three spaces of indentation, which CommonMark allows for a paragraph) and [ordering] (trailing spaces, removed from a paragraph by CommonMark). The other tags allow both: essay essay : ws? "[essay]" ws?, numeric answer : ws? "[" "numeric" ..., short-answer accept_block : ws? "[" "short-answer" .... docs/references/grammar.md:59-69 defines the ws? at the start of a block as the CommonMark indentation, so its absence here is a deliberate-looking restriction that the prose does not state. mdq-py accepts both inputs.

Impact: Readers cannot tell whether indentation or trailing spaces on the tag line are an error. The grammar and the reference implementation disagree.

Suggested fix: Write ws? "[" "ordering" "]" ws? nl, as the essay tag does.

medium F3: Ordering grammar rejects a blank line between [ordering] and its content block

Location: docs/question-types/ordering.md:141

ordering : "[" "ordering" "]" nl content epilogue? section*

Description: After the tag there is exactly one nl, so the input [ordering] / blank line / fenced code block (or ul list) is REJECTED. The section rules of the same snippet use nl+ after the heading (docs/question-types/ordering.md:146-148), so a blank line is allowed there and not after the tag. The prose ("an [ordering] tag followed either by a code block or a markdown ul element") does not forbid the blank line, and mdq-py accepts it.

Impact: Same snippet, two different rules for the same layout. An implementer who follows the grammar rejects documents that mdq-py accepts.

Suggested fix: Decide whether a blank line may separate the tag from its block. If yes, use blank_line* after the tag line; if no, state it in prose and add an invalid example.

medium F4: Ordering section headings reject CommonMark ATX variants and whitespace-only blank lines

Location: docs/question-types/ordering.md:146-148, docs/question-types/essay.md:99-100

ordering_extra  : "##" ws "[" "extra" "]" nl+ content
ordering_accept : "##" ws "[" "accept" "]" nl+ (observations blank_line*)? content
ordering_reject : "##" ws "[" "reject" "]" nl+ (observations blank_line*)? content

Description: The heading rules have no ws? before ## or after ], no closing sequence, and use nl+ instead of blank_line*. The grammar REJECTS: ## [extra] (indentation of up to three spaces), ## [extra] (trailing spaces), ## [extra] ## (ATX closing sequence), and ## [extra] followed by a line of only spaces before the content block.
