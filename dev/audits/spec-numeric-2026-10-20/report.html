Strengths and weaknesses

Strengths

  • Grammar violations: The numeric answer grammar accepts all 32 tag lines of the valid numeric corpus and rejects every invalid numeric corpus line except 1/0. Number literals have no leading zeros, no leading or trailing dot, no exponent, and the sign must touch the value. Rejected (Lark, Earley): [numeric()]: 60, 3e5, .5, 007, 8., 26 +- -1, [numeric (kg)]: 60, 60 kg, 3.14 +- 5% +- 10%, [numeric(k[g])]: 60, [numeric(k g)]: 60, U+00A0 after the colon, - 5, 00.5, 1 / 3, 1.5/2. Accepted: -0, +26, 0.50. (docs/question-types/numeric.md:66-79)
  • Grammar violations: The tolerance grammar allows at most one absolute and one relative tolerance in either order, with optional spaces, and never a fraction or a sign in a tolerance. This agrees with the prose, the domain table and tolerance.absolute (a number, minimum 0) in the schema. Accepted: 3.14 +- 5% +- 0.1, 3.14 +- 0.1 +- 5%, [numeric]:3.14+-0.1+-5%, 42+-1, 5 +-0%. Rejected: 5 +- 1 +- 2, 3.14 +- 5% +- 10%, 1/3 +- 1/10, 5 +- 5 %, +- 5, 5 +- 1.5e2. (docs/question-types/numeric.md:69-76, docs/question-types/numeric.md:122-131, schema/numeric.yaml:76-90)
  • Grammar violations: UNIT excludes exactly the 25 code points of UNICODE_SPACE and the four brackets, the unit pattern of the schema is the same class, and the Unit conversion prose states the same rule. Accepted: °C, km/h, R$, hab/km². Rejected: empty unit, k g, k[g], a space before (, (kg)(m). (docs/references/grammar.md:89, docs/references/grammar.md:200, schema/numeric.yaml:36, docs/question-types/numeric.md:184-189)
  • Grammar violations: The string pattern of answer in the schema matches sign? value of the grammar (sign, INTEGER, DECIMAL, fraction), and also rejects a zero denominator as the Answer representation prose requires. (schema/numeric.yaml:29, docs/references/grammar.md:87-88, docs/question-types/numeric.md:71-78, docs/question-types/numeric.md:109-110)
  • Grammar violations: All 12 numeric_def lines of the valid fill-in corpus parse with the numeric body grammar, with units and both tolerances, for example [^litoral/numeric(km)]: 7400 +- 100 +- 2% and [^densidade/numeric(hab/km²)]: 23.86 +- 0.5. (docs/question-types/fill-in.md:158, docs/question-types/fill-in.md:201)
  • Inconsistencies: The UNIT terminal agrees in numeric.md, grammar.md and both schemas: any character except UNICODE_SPACE and the four brackets, with corpus cases for non-ASCII, slash, bracket, space and empty units. (docs/question-types/numeric.md:184-189, docs/references/grammar.md:89, schema/numeric.yaml:36, examples/valid/numeric/unit-non-ascii.mdq.md, examples/invalid/numeric-unit-with-bracket.mdq.md)
  • Ambiguities: Tolerance boundaries are inclusive (<=) and the grading vectors test both edges of absolute and relative tolerances, negative answers and the zero answer. (docs/question-types/numeric.md:151-153, examples/grading/numeric.yaml (Absolute tolerance, Relative tolerance, Negative answer, Zero answer))
  • Omissions: Domain inference is a total table with a rank order, and every row has a corpus example (integer, decimal tolerance, fraction with integer and decimal tolerance, declared wider domain). (docs/question-types/numeric.md:122-138, examples/valid/numeric/fraction-integer-tolerance.mdq.md, examples/valid/numeric/fraction-decimal-tolerance.mdq.md, examples/valid/numeric/domain-decimal-integer-answer.yaml)
  • Contradictions: The rounding mode is fully specified (half away from zero, in decimal arithmetic) with a binary-float trap as example, and the grading vectors test it (2.675 to 2.68). (docs/question-types/numeric.md:162-165, examples/grading/numeric.yaml (Explicit decimal places))
  • Schema mismatches: Schema constraints match the Additional Rules: decimalPlaces and both tolerances have minimum 0, the answer string pattern is the sign? value grammar with a nonzero denominator, and invalid examples cover the negative cases. (schema/numeric.yaml:29, schema/numeric.yaml:47, schema/numeric.yaml:82, schema/numeric.yaml:90, examples/invalid/numeric-negative-absolute-tolerance.yaml, examples/invalid/numeric-negative-decimal-places.yaml)
  • Omissions: The complete Markdown examples of numeric.md and of the numeric blank of fill-in.md validate with no error in mdq-py. (docs/question-types/numeric.md:8-12, docs/question-types/fill-in.md:214-218)

Central risks

  • The numeric grading vectors assume exact decimal arithmetic and the shortest decimal form of floats, but the text requires neither, so a conforming float implementation fails the shared vectors on tolerance boundaries.
  • Unit handling is optional (MAY) and the outcome of a foreign unit is both an error and a score, so the same response can be graded, scored 0 or rejected depending on the host.
  • Rules that depend on how a number is spelled (domain and decimalPlaces inference) have no defined meaning for YAML and JSON documents, which are the canonical AST.

high F5: A response with a foreign unit is both malformed and scored 0

Location: docs/responses.md:133-142

Implementations MAY do unit conversions and rewrite the response to a canonical
form, but they MUST reject a response with a unit that is not compatible with
the question's unit with grade zero.

Description: Line 137-139 says a response with an incompatible unit is rejected "with grade zero" (a score). Line 141-142 says "a unit other than the declared one" is a malformed response, which is an error and never a score ("Errors"). Since conversion is MAY, {value: 1, unit: kg} for a g question is a score of 1 (after conversion), a score of 0, or a ResponseError, depending on the implementation. A response without a unit for a question that declares one is not covered. How two units are compared (exact string, NFC, case) is not defined.

Impact: The same response gets a score in one implementation and an error in another.

Suggested fix: Decide one rule: (a) a unit other than the declared one is always malformed, and conversion is outside the spec; or (b) define compatible units and the conversion, and malformed only for incompatible ones. State that a bare number is in the declared unit, and how units compare.

medium F9: missing-tolerance fires on fraction answers, where an exact match is meaningful

Location: docs/question-types/numeric.md:218, docs/question-types/numeric.md:229-230

| tolerance          | info     | missing-tolerance              | is not defined for a `decimal` or `fraction` answer[^5]            |

Description: Footnote 5 justifies the rule with "the number of digits the student types decides the outcome". This is true for a decimal answer, but a fraction question compares exact rationals: 1/3 accepts "1/3" and "2/6" (examples/grading/numeric.yaml, "Fraction"), and no digit count is involved. A tolerance on a fraction question also changes its domain to decimal (table at line 122-128) when written as a decimal.

Impact: Every exact fraction question gets a lint that suggests a change that turns it into a decimal question.

Suggested fix: Restrict missing-tolerance to the decimal domain, or rewrite the footnote with a reason that holds for fractions.

high F1: The arithmetic of the tolerance test is not defined

Location: docs/question-types/numeric.md:151-157

* Absolute tolerance: The response is accepted if `|answer - response| ≤ abstol`.

Description: The spec says that rounding to decimalPlaces is done in decimal arithmetic (line 163), but it does not say how |answer - response| and |answer| x relative are computed. In binary floating point, 3.15 - 3.14 is 0.010000000000000231, so 3.14 +- 0.01 rejects 3.149 (rounded to 3.15). examples/grading/numeric.yaml, "Rounding to inferred decimal places", expects score 1 for 3.149: the vectors assume exact (decimal or rational) arithmetic that the text does not require. The same holds for a fraction answer with a relative tolerance.

Impact: Two implementations that both follow the text give different scores on the boundary of every decimal tolerance, which is where authors put their tolerances.

Suggested fix: State that the tolerance test is exact: the answer, the response and both tolerances are read as exact rationals (a decimal as written, a float by its shortest decimal form), and the comparison is done on these rationals.

high F2: How a float response is read before decimal rounding is not defined

Location: docs/question-types/numeric.md:162-164

many decimal places, half away from zero, in decimal arithmetic (never in
binary floating point: `2.675` rounds to `2.68`). A response with more digits

Description: A response is a JSON number or a string (responses.md, "Numeric"). The JSON number 2.675 is the double 2.67499999999999982236431605997495353221893310546875. Rounded in decimal arithmetic from that exact value it gives 2.67; from its shortest decimal form 2.675 it gives 2.68. examples/grading/numeric.yaml, "Explicit decimal places", expects 2.675 (a YAML float) to score 1, so the vectors assume the shortest decimal form. The text does not say it.

Impact: A response sent as a number and the same response sent as a string can score differently, and so can two implementations.

Suggested fix: In responses.md and numeric.md, state that a number response is read as the shortest decimal string that round-trips to the same double, and that this decimal is the value used for rounding and for the tolerance test.

medium F26: The relative tolerance is not defined against the rounded or the unrounded answer

Location: docs/question-types/numeric.md:155-157

If both tolerances are defined, a response is accepted if it passes ANY of those
criteria. When the domain is `decimal`, the response and the answer are first
rounded to [`decimalPlaces`](#decimal-places).

Description: The answer is rounded before the tolerance test, but the text does not say if |answer| × relative uses the rounded answer, and if the tolerances are rounded too. With answer: 0.04, decimalPlaces: 1 and relative: 0.5, the rounded answer is 0.0: the relative tolerance becomes 0 and only 0.0 passes, while the unrounded answer gives a tolerance of 0.02. relative-tolerance-around-zero checks only an answer equal to 0, not one that rounds to 0. No vector in examples/grading/numeric.yaml combines a relative tolerance with rounding.

Impact: Implementations can accept different responses for the same question.

Suggested fix: State which value the relative tolerance uses (for example, the answer before rounding), and whether the tolerances are rounded; add a grading vector for it.

medium F3: decimalPlaces is inferred only from a Markdown body

Location: docs/question-types/numeric.md:117-118, docs/question-types/numeric.md:169-173

When the frontmatter does not give `decimalPlaces` and the domain is
`decimal`, it is inferred from the body: the larger of the number of decimal

Description: A YAML or JSON question has no body, and most YAML/JSON libraries do not keep how a number is spelled. The decimalPlaces rule (line 169-173) does not say what decimalPlaces is for {answer: 3.14, tolerance: {absolute: 0.01}} or {answer: 5, domain: decimal}. examples/grading/numeric.yaml infers it from the YAML values ("Rounding to inferred decimal places": 2 places; "Declared decimal domain": 0 places), so a YAML float is counted by its shortest decimal form, and a YAML integer counts 0. The domain inference (line 117-118) has the same gap: "how the value and the absolute tolerance are written" has no meaning for a number in JSON. In Markdown 4.0 is a DECIMAL; in YAML answer: 4.0 is a whole float, and the text does not say if it infers integer or decimal. Footnote 3 says that domain-mismatch reads values ("4.0 is whole"), but it does not cover inference. The inferred domain decides if 4.5 is malformed (integer) or graded (decimal).

Impact: An implementation that leaves decimalPlaces unset for YAML input, or reads it from a float's full binary expansion, grades differently from the vectors.

Suggested fix: Define both inferences over the answer and the absolute tolerance as values: a string by its digits as written, a number by its shortest decimal form (an integer counts 0 places).

medium F4: The response forms accepted by each domain are not specified

Location: docs/responses.md:110-123, docs/responses.md:141-143

A string carries an exact rational, which no float can represent. It MUST be
used when the question's `domain` is `fraction` and the value is not exactly
representable as a decimal:

Description: responses.md gives one example of a malformed value (a decimal for an integer domain) but no rule per domain. The vectors fix answers the text does not give: for domain: fraction, the decimal responses 0.3333 and "0.5" score 0 and are not malformed; for an integer domain, "1/2" is malformed. It is not stated whether a fraction string is valid for a decimal question, whether "4/2" or 4.0 is valid for an integer question (footnote 3 of numeric.md says the lint reads values, so 4.0 is whole), or whether exponents (1e3, "1e3") and a leading + are accepted in a string response. The sentence "The string MUST be a valid decimal" (line 119) also excludes integer strings such as "1822", which the vectors accept.

Impact: Implementations disagree on which responses are malformed and which are scored, which changes the student's grade or the error the host gets.

Suggested fix: Add a table to responses.md, "Numeric": for each domain, which response forms are valid (integer, decimal, fraction, number, string) and which are malformed, with the string grammar (sign? value of numeric.md or a stated extension).

medium F10: Numeric questions have no feedback for responses

Location: docs/question-types/numeric.md:192-202

Grading is binary: a response inside the accepted tolerance scores 1, and any
other response scores 0.

Description: Short answer has reject patterns with feedback and incorrectFeedback; choice lists have feedback per choice. A numeric question has no way to attach feedback to an incorrect response, not even a fixed incorrectFeedback, and no way to recognize a known wrong answer (for example, a unit error of a factor 1000). The spec does not say that this is intended.

Impact: Authors move numeric questions to short-answer regexes to give feedback, and lose tolerance and domain checks.

Suggested fix: Either state that numeric has no feedback by design, or add incorrectFeedback (as in short-answer and the blanks of fill-in) and, optionally, reject values with tolerance and feedback.

medium F11: No grading vector covers units

Location: examples/grading/numeric.yaml:1-20

#   examples: { response: number | string, score: 0 | 1 | "malformed" }[]

Description: The response type in the header of the vector file does not include the {value, unit} form of responses.md, line 125-131, and no vector has a unit. The malformed cases for a unit (a unit on a question without one, a unit other than the declared one) are not tested.

Impact: The unit rules of responses.md have no shared test, so implementations can drift.

Suggested fix: After the unit rule is decided, add the {value, unit} form to the header and vectors for each case.

medium F19: Non-finite answers (infinity, NaN) are not excluded

Location: docs/question-types/numeric.md:107-108

A document written directly as JSON/YAML/dict, rather than parsed from
Markdown, can choose freely between numeric and string representations.

Description: A YAML document can give answer: .inf or answer: .nan. The spec does not exclude them, and schema/numeric.yaml:27 (type: number) accepts them. The domain table, the tolerance test and the rounding are not defined for these values. mdq validate --format yaml on {type: numeric, stem: x, answer: .inf} crashes with OverflowError: cannot convert float infinity to integer, and .nan exits with error: cannot convert float NaN to integer.

Impact: Implementations behave differently on such documents: the reference one crashes instead of reporting a diagnostic.

Suggested fix: State that answer and the tolerances are finite numbers, and give the error code for a non-finite value.

Exploitability conditions: A YAML or JSON document (YAML has .inf and .nan; some JSON parsers accept Infinity and NaN).

medium F20: A numeric blank in Markdown cannot declare domain or decimalPlaces

Location: docs/question-types/fill-in.md:204-209

The `numeric_body` and `unit` non-terminals represent, respectively, a numeric
value with tolerance and an optional unit of measurement. Both are defined in
the [body](numeric.md#body) section of the numeric question type. The `blank`

Description: NumericBlank in schema/fill-in.yaml has domain and decimalPlaces, and numeric.md sets both in the frontmatter. The fill-in frontmatter table has no field for them, and the numeric_def syntax has no place for them. So a Markdown numeric blank always gets the inferred domain and places. The spec does not say that this limit is intended, and no example in examples/valid/fill-in/ sets them.

Impact: An author cannot write a decimal blank with an integer answer (42 in a decimal domain), or set the precision of a blank, in Markdown. The YAML form can express questions that the Markdown form cannot.

Suggested fix: Either state that a Markdown numeric blank always uses the inferred domain and places, or add a frontmatter map (blank id to domain/decimalPlaces), as fill-in already does for preAccept and incorrectFeedback.

low F23: SHOULD rules of Answer representation are not in Additional Rules

Location: docs/question-types/numeric.md:90-91, docs/question-types/numeric.md:100-102

An integer number like `42` or `-1` SHOULD be coerced to an integral value.
It SHOULD be kept as a string if it is not representable in the 32-bit signed
integer range.

Description: "Numeric conversions SHOULD NOT be attempted when there is loss of precision" (line 90-91) and the two SHOULD rules of line 100-102 have no row in the Additional Rules table. They are rules for the parser output, not for the document, so no lint code can report them, but the spec does not say this.

Impact: The requirement levels in the text and in the table do not agree.

Suggested fix: State that the rules of "Answer representation" apply to the parser output and have no diagnostic, or reword them without RFC 2119 keywords.

low F25: The Tolerances section does not map a percentage to tolerance.relative

Location: docs/question-types/numeric.md:152-153

where tol is calculated as `|answer| × percentage_number ÷ 100`.

Description: The formula uses the percentage as written in Markdown. The YAML/JSON form stores tolerance.relative as a fraction (0.05 for 5%), but numeric.md says this only in footnote 4 of the Additional Rules ("0.05 is 5%") and footnote 2 uses |answer| × relative. The section does not give the formula for the stored field.

low F6: Unclear sentence about decimal string responses

Location: docs/responses.md:118-119

The response of a decimal value may also be represented as a string, which

Description: "which systems MAY flag the system to use decimal arithmetic" is not a correct sentence, and it suggests that the arithmetic depends on whether the response is a string. high F12: The fraction rule accepts a zero denominator that the corpus rejects as parse-error

Location: docs/question-types/numeric.md:78, docs/question-types/numeric.md:109-110

Mechanical fix

fraction     : INTEGER "/" INTEGER

Description: INTEGER matches 0, so the grammar accepts [numeric]: 1/0 (tested with Lark, Earley parser). The corpus case examples/invalid/numeric-zero-denominator.mdq.md expects parse-error for that input, and the schema pattern of answer in schema/numeric.yaml uses [1-9][0-9]* for the denominator. The only prose rule about a zero denominator (numeric.md:109-110) applies to documents written directly as JSON/YAML, and the Additional Rules table maps it to malformed-numeric-answer, which examples/invalid/numeric-malformed-fraction-answer.lint.json expects for answer: "1/0". So the same defect has two codes, and only one is stated in the spec.

Impact: An implementation that follows the grammar accepts 1/0 and then reports malformed-numeric-answer or schema-error, so it fails the corpus case. The spec gives three different outcomes for one input.

Suggested fix: Use a terminal with no zero for the denominator, for example fraction : INTEGER "/" DENOMINATOR with DENOMINATOR : /[1-9][0-9]*/, as the schema pattern and the corpus already do.

Exploitability conditions: Markdown body with a fraction whose denominator is 0.

medium F13: numeric_def has no leading ws?, unlike the numeric answer and the other blank definitions

Location: docs/question-types/fill-in.md:158, docs/question-types/fill-in.md:201

numeric_def      : "[^" SLUG "/numeric" unit? "]" ws? ":" ws? numeric_body

Description: answer of numeric (numeric.md:67) and accept_def and reject_def of fill-in (fill-in.md:159-160) start with ws?. numeric_def at line 158 and line 201 does not. With Lark, [^a/numeric]: 5 (three spaces of indentation, a valid CommonMark paragraph start) is rejected by numeric_def, but [numeric]: 5 is accepted by answer and [^a/short-answer]: x by accept_def.

# [Spec] Define numeric values and the tolerance test in exact arithmetic

**Labels:** high, medium

## Problem

The tolerance test, the reading of float responses, the inference of domain and decimalPlaces from YAML values, and the base of the relative tolerance are not defined. Options: (a) recommended: every number (answer, response, tolerances) is an exact rational; a float is read by its shortest round-trip decimal form; inference reads that form (a whole number with no decimals is integer); the relative tolerance uses the answer before rounding; tolerances are not rounded. (b) Allow floating point and add an epsilon to the comparison; simpler to implement but the vectors and the 2.675 example must change.

## Evidence

- `docs/question-types/numeric.md:151-157`: The arithmetic of the tolerance test is not defined

  ```markdown
  * Absolute tolerance: The response is accepted if `|answer - response| ≤ abstol`.
  ```
- `docs/question-types/numeric.md:162-164`: How a float response is read before decimal rounding is not defined

  ```markdown
  many decimal places, half away from zero, in decimal arithmetic (never in
  binary floating point: `2.675` rounds to `2.68`). A response with more digits
  ```
- `docs/question-types/numeric.md:117-118, docs/question-types/numeric.md:169-173`: decimalPlaces is inferred only from a Markdown body

  ```markdown
  When the frontmatter does not give `decimalPlaces` and the domain is
  `decimal`, it is inferred from the body: the larger of the number of decimal
  ```
- `docs/question-types/numeric.md:155-157`: The relative tolerance is not defined against the rounded or the unrounded answer

  ```markdown
  If both tolerances are defined, a response is accepted if it passes ANY of those
  criteria. When the domain is `decimal`, the response and the answer are first
  rounded to [`decimalPlaces`](#decimal-places).
  ```

## Impact

- **The arithmetic of the tolerance test is not defined:** Two implementations that both follow the text give different scores on the boundary of every decimal tolerance, which is where authors put their tolerances.
- **How a float response is read before decimal rounding is not defined:** A response sent as a number and the same response sent as a string can score differently, and so can two implementations.
- **decimalPlaces is inferred only from a Markdown body:** An implementation that leaves `decimalPlaces` unset for YAML input, or reads it from a float's full binary expansion, grades differently from the vectors.
- **The relative tolerance is not defined against the rounded or the unrounded answer:** Implementations can accept different responses for the same question.

## Suggested fix

- **The arithmetic of the tolerance test is not defined:** State that the tolerance test is exact: the answer, the response and both tolerances are read as exact rationals (a decimal as written, a float by its shortest decimal form), and the comparison is done on these rationals.
- **How a float response is read before decimal rounding is not defined:** In responses.md and numeric.md, state that a number response is read as the shortest decimal string that round-trips to the same double, and that this decimal is the value used for rounding and for the tolerance test.
- **decimalPlaces is inferred only from a Markdown body:** Define both inferences over the answer and the absolute tolerance as values: a string by its digits as written, a number by its shortest decimal form (an integer counts 0 places).
- **The relative tolerance is not defined against the rounded or the unrounded answer:** State which value the relative tolerance uses (for example, the answer before rounding), and whether the tolerances are rounded; add a grading vector for it.

## Acceptance criteria

- [ ] numeric.md states the arithmetic of rounding and of the tolerance test
- [ ] responses.md states how a number response is read
- [ ] Inference of domain and decimalPlaces is defined for YAML/JSON values
- [ ] Grading vectors cover a relative tolerance with rounding and a float on a tolerance boundary
