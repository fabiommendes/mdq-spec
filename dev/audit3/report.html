Date: 2026-10-09

Scope: Specification of the numeric and ordering question types: docs/question-types/numeric.md, docs/question-types/ordering.md, their schemas schema/numeric.yaml and schema/ordering.yaml, and the shared documents they depend on (question-base.md, references/grammar.md, references/patterns.md, exam.md, responses.md).

Methodology

The audit covers the numeric and ordering question types of the MDQ specification: their documents in docs/question-types/, their JSON schemas in schema/, and the shared documents they depend on (question-base.md, references/grammar.md, responses.md, exam.md, lint-codes.md). scripts/spec_audit.py passed all 14 steps before the audit started.

The lead auditor read every in-scope document and recorded contradictions, ambiguities, omissions, inconsistencies and schema mismatches. One subagent converted each Lark grammar into a runnable grammar with stub rules and tested what it accepts and rejects with Lark 1.3.1, and cross-checked the token regexes in Python re, JavaScript RegExp and JSON Schema validators. Two further subagents, one per question type and without the lead's notes, reviewed each type independently, compared it with its schema, checked the corpus under examples/, and ran every complete Markdown example through mdq validate (mdq-py).

Spelling and grammar mistakes were fixed in place without moving lines. Findings outside the two question types (short-answer grammar and pattern strings) were dropped as out of scope.

Strengths and weaknesses

Strengths

  • Grammar violations: UNICODE_SPACE is exactly the Unicode White_Space property, and it matches the same 25 code points in Python re and in JavaScript RegExp with and without the u flag. Checked by matching every code point from U+0000 to U+10FFFF (surrogates skipped) and comparing with /\p{White_Space}/u in Node 22 (/tmp/grammar-audit/cls.py, cls.js). (docs/references/grammar.md:80-89)
  • Grammar violations: The tokens ws, nl, SLUG, INTEGER, DECIMAL, UNIT and COMMENT_LINE accept the same strings in Python re and in JavaScript RegExp (with and without u) on 55 inputs: empty string, 0, 00, 007, -1, .5, 5., 1e3, Arabic-Indic and fullwidth digits, a-b, a--b, -a, a-, a_-b, Amazônia, space, tab, CRLF, CR, LF, LF CR, U+2028, U+0085, form feed, comments with CR, CRLF and an embedded U+2028, km/h, µm, °C, Ω, astral characters (U+1D707, emoji), U+00A0, U+200B, U+FEFF, U+001F, NUL and brackets. UNIT with + also matches astral characters in non-u mode, since it accepts both surrogate halves. INTEGER and DECIMAL reject signs, leading zeros, exponents and non-ASCII digits as grammar.md:69 states (/tmp/grammar-audit/tok.py, tok.js). (docs/references/grammar.md:58-75)
  • Grammar violations: No Lark snippet in docs/ uses the shorthand classes \s, \d or \w, and the exam TAG terminal excludes the same 25 UNICODE_SPACE code points as grammar.md:83-85 states (checked by grep over every ```lark block of docs/question-types/ and docs/exam.md). (docs/exam.md:206)
  • Grammar violations: The numeric grammar accepts every body example of numeric.md (42, 3.14, 3.14 +- 0.1, 3.14 +- 5%, 3.14 +- 5% +- 0.1, -1/3, [numeric(kg)]: 5.5 +- 0.1) plus +42, -0, 2.50, the reverse tolerance order, indentation, spaces around the colon, no spaces around +-, and the units µm, °C, km/h, Ω. It rejects empty input, an empty answer, 007, .5, 5., 1e3, '- 1', --1, 1/-3, 1.5/2, 1,5, 1_000, '1 000', negative and fraction tolerances, two absolute or two relative tolerances, ±, spaces inside the brackets, '[numeric (kg)]', empty and spaced units, units with parentheses, U+00A0 as whitespace, fullwidth and Arabic-Indic digits, a trailing newline and trailing text. No input produced an ambiguous parse with the dynamic or dynamic_complete lexer (Lark 1.3.1, /tmp/grammar-audit/test_numeric.py). The only defect found is the zero denominator. (docs/question-types/numeric.md:63-76)
  • Grammar violations: The ordering observation rules enforce the stated rules: feedback and comment in either order are accepted; '> f1 ! c > f2', '! c > f ! c2' and two feedback blocks split by a blank line are rejected; '[ ordering ]', '##[accept]', prose between the block and a section, and a section without a content block are rejected (/tmp/grammar-audit/test_more.py). (docs/question-types/ordering.md:146-155)
  • Schema mismatches: The numeric answer string pattern, the unit pattern and the minimum: 0 constraints of the schema match the sign? value grammar, the UNIT terminal and the Additional Rules table. (schema/numeric.yaml:26-36, schema/numeric.yaml:45-47, schema/numeric.yaml:77-90)
  • Omissions: Every numeric lint code of the Additional Rules table is exercised by the corpus, and the grading corpus covers rounding, both tolerances, negative and zero answers, and malformed responses. (examples/grading/numeric.yaml:17-185)
  • Omissions: Both complete Markdown examples of ordering.md (the minimal Fibonacci question and the full example with strict indentation, extra, accept and reject) pass mdq validate with no warning. (docs/question-types/ordering.md:16-89)
  • Omissions: Every ordering lint code of the Additional Rules table has a corpus example, including model-only examples for accept-reject-overlap and parse-error examples for type mismatch, two extras, interleaved observations, multi-line items and ordered lists. (docs/question-types/ordering.md:352-372)
  • Schema mismatches: The enums and defaults of indentation, unmatched and normalizations, the [level, text] line shape with a non-negative integer level, uniqueItems on normalizations and minItems: 2 on lines match the frontmatter footnotes and the Additional Rules table. (schema/ordering.yaml:17-156)

Central risks

  • Numeric grading of boundary responses and of responses with units depends on the implementation: the spec does not fix the arithmetic of the tolerance test and gives two incompatible rules for units.
  • The ordering rules on "the same lines" read literally as a multiset, which would make common valid questions fail with a critical accept-reject-overlap.
  • Several grammars in scope reject documents that the prose and the corpus declare valid (indented [ordering] tag, blank line before a section), so an implementation that follows the grammar fails the shared test suite.
  • The mapping from the Markdown body to the AST fields (answer, tolerance, lines, extra, accept, reject) exists only in the schemas and the corpus, so a new implementation must reverse-engineer it.

high F1: A response unit other than the declared one is both convertible and malformed

Location: docs/responses.md:129-135

Implementations MAY do unit conversions and rewrite the response to a canonical
form, but they MUST reject a response with a unit that is not compatible with
the question's unit with grade zero.

A value the question cannot represent is a malformed response, never a wrong
answer: a decimal where `domain` is `integer`, or a unit other than the
declared one.

Description: Line 129 lets an implementation convert a compatible unit (numeric.md "Unit conversion" gives 1kg for a g question). Line 133 says any unit other than the declared one is malformed. Line 130 also says an incompatible unit is both "rejected" and graded zero, while the Errors table says a response the question cannot represent raises ResponseError, never a score.

Impact: For [numeric(g)]: 1000 and the response {value: 1, unit: kg}, one implementation scores 1, another raises ResponseError. For {value: 1, unit: s}, one scores 0 and another raises an error.

Suggested fix: State one rule: a unit equal to the declared one is valid; a different unit that the implementation can convert is converted before grading; any other unit is a malformed response (ResponseError), not a zero. Remove "with grade zero" and "or a unit other than the declared one".

medium F2: Ordering puts the epilogue after its sections; the base puts special sections after the epilogue

Location: docs/question-types/ordering.md:181-183

The sections below follow the content block directly. The epilogue, if any,
comes after the last section; prose between the block and a section is an
error (`parse-error`).

Description: question-base.md:4-6 and :230-231 fix the order frontmatter, introduction, body, epilogue, then the question-specific sections. Ordering requires the ## [extra], ## [accept] and ## [reject] sections right after the body and the epilogue after them. The ordering grammar (ordering.md:141) has no epilogue at all.

Impact: An author following the base document writes the epilogue before ## [accept] and gets a parse-error. Readers cannot tell which document is normative.

Suggested fix: Make question-base.md describe the type-specific sections as part of the body (or as coming before the epilogue), and add the epilogue to the ordering grammar.

high F3: "Hold the same lines" can mean the same multiset or the same sequence

Location: docs/question-types/ordering.md:208-212

A question SHOULD NOT declare two sections whose content
blocks hold the same lines once **all forms of normalization** have been
applied

Description: Every alternative of an ordering question is usually a permutation of the same lines. Read as "the same set of lines", the MUST NOT forbids almost every question that has both an accepted and a rejected ordering (a reject is typically the correct lines in a wrong order). The intended reading is "the same lines in the same order". The same wording is used by accept-reject-overlap, duplicate-alternative-lines and accept-repeats-answer-key (ordering.md:358, :366-367, lint-codes.md:13, :24, :75).

Impact: An implementation that reads it as a multiset raises a critical accept-reject-overlap on valid questions.

Suggested fix: Write "the same sequence of lines (same lines, same order)" in the prose, in the three Additional Rules rows and in lint-codes.md.

high F4: Indentation of ul lines is not defined

Location: docs/question-types/ordering.md:261-266

The **indentation unit** is inferred from the lines of the question. It
considers all lines in the `[ordering]`, `## [extra]`, `## [accept]` and
`## [reject]` blocks, normalizes a tabulation as 4 spaces, and takes the
greatest common divisor of the leading whitespace of every non-blank line that
is indented at all.

Description: For a code block, "leading whitespace" is clear. For a ul list it is not: the spaces before the - marker, list nesting, or spaces after the marker. A nested list item is also a continuation of its parent in CommonMark, and ordering.md:167-168 makes an item with continuation lines a parse-error. So it is unclear whether text content can have levels other than 0. Also unspecified: whether a tab counts as 4 spaces or advances to the next tab stop (" \t" is 6 or 4), and what level a whitespace-only line has.

Impact: Two implementations give different [level, text] pairs for the same ul question, so the same response grades differently.

Suggested fix: State that text content is always at level 0 (nested lists are a parse-error), or define levels from list nesting. Define tab expansion and the level of a blank line.

high F8: Tolerance comparison arithmetic is not specified

Location: docs/question-types/numeric.md:148-154

* Absolute tolerance: The response is accepted if `|answer - response| ≤ abstol`.

Description: Only rounding is required to use decimal arithmetic (numeric.md:160-161). The subtraction and the ≤ test are not. In binary floating point, [numeric]: 3.14 +- 0.1 with the response 3.24 gives |3.14 - 3.24| = 0.10000000000000009 > 0.1, so a response exactly on the boundary is rejected; in decimal arithmetic it is accepted. The same applies to the relative tolerance and to a numeric response written as a float (2.675 as a JSON number is 2.67499999...).

Impact: Responses on the tolerance boundary grade differently across implementations and languages.

Suggested fix: Require the whole tolerance test to run in exact decimal/rational arithmetic, with a JSON number read as its shortest decimal representation.

medium F6: Declared content that disagrees with the body block has no meaning

Location: docs/question-types/ordering.md:106-108

[^1]: `content = "code" | "text"`. Both fields are OPTIONAL, and when given
they override what the body implies.

Description: content: text over a fenced code block, or content: code over a ul, "overrides" the body, but the spec does not say what that does: whether lines are still split per code line or per list item, whether highlight then applies, or whether it is an error. "Both fields" also refers to content and highlight from a footnote attached only to content. The schema adds default: text (schema/ordering.yaml:60), which the prose never mentions.

Impact: Implementations can accept, reject, or reinterpret the same document.

Suggested fix: Make a mismatch between declared content and the body block a parse-error (or a warning with a defined effect). Document the text default for documents written as YAML/JSON.

medium F7: Ordering score is "always binary" but a pending response is scored by hand

Location: docs/question-types/ordering.md:326-332

The score is always binary -- `1` or `0`, with no partial credit for a nearly
correct ordering.

Description: Under unmatched: manual the instructor supplies the score of a pending response. The spec does not say whether that score must also be 0 or 1, or can be any value in [0, 1] (the essay case).

Impact: A host may refuse a partial manual score that another host accepts.

Suggested fix: State that the binary rule applies to automatic grading only, and that a manual score is any value in [0, 1] (or restrict it explicitly).

medium F9: Inferred decimalPlaces of 0 turns a declared decimal domain into rounding to integers

Location: docs/question-types/numeric.md:166-169

When the frontmatter does not give `decimalPlaces` and the domain is
`decimal`, it is inferred from the body: the larger of the number of decimal
places written in the value and in the absolute tolerance.

Description: With domain: decimal declared and [numeric]: 42 (or 1/3) and no absolute tolerance, the rule gives decimalPlaces: 0. Both sides are then rounded to integers: 41.6 rounds to 42 and is accepted, and for 1/3 every response in [-0.5, 0.5) is correct. The spec does not say whether this is intended, and no lint reports it.

Impact: A question meant to be strict silently accepts a wide range.

Suggested fix: Specify the result for a value with no written decimal places (for a fraction, an exact comparison or a lint), or add a lint when the inferred decimalPlaces is 0 under a declared decimal domain.

medium F12: Numeric response forms are underspecified

Location: docs/responses.md:102-111

A string carries an exact rational, which no float can represent. It MUST be
used when the question's `domain` is `fraction` and the value is not exactly
representable as a decimal:

Description: Unspecified: whether a fraction question accepts a decimal response (0.5 for 1/2) and how a decimal response that approximates a fraction (0.333) is graded; whether "4/2" or "2/4" is valid where an integer or a reduced fraction is expected; whether a decimal string may be an integer ("3") and what grammar it follows. Line 111 is garbled ("which systems MAY flag the system to use decimal arithmetic"). The table at line 30 lists only a number or a rational string, and omits the decimal string and the {value, unit} struct. Line 125-127 says a response unit is malformed when the question has no unit, but does not say whether a unitless response to a question with a unit is valid.

Impact: Implementations disagree on which responses are malformed and which are graded.

Suggested fix: Specify the response grammar per domain (reuse sign? value), the treatment of unreduced fractions and unitless responses, and update the table at line 30.

medium F29: Domain and decimal-place inference from a JSON/YAML number is undefined

Location: docs/question-types/numeric.md:114-115, docs/question-types/numeric.md:166-168, docs/question-types/numeric.md:101-102

If not given in the frontmatter, the domain is inferred from how the value and
the absolute tolerance are written

Description: Inference reads how numbers are written (8 +- 1.0 is decimal with 1 place, examples/valid/numeric/whole-decimal-tolerance). A document written directly as YAML/JSON may omit domain and decimalPlaces (the grading corpus does), but a YAML or JSON number does not keep its spelling: 1.0 and 1, 2.50 and 2.5 are the same value. mdq-py infers integer for {answer: 8, tolerance: {absolute: 1.0}} and rejects the response 8.5 as malformed, while the Markdown [numeric]: 8 +- 1.0 gives a decimal question that accepts it. The answer 2.50 (number) infers 1 place, the string "2.50" 2 places, which contradicts line 101-102 (the domain is unaffected by the representation).

Impact: The same question grades differently depending on whether it was written in Markdown or as data, and across YAML/JSON libraries.

Suggested fix: State that for data documents inference reads values, not spelling (a whole number is an integer, decimal places of the shortest representation), or require domain and decimalPlaces in data documents.

medium F39: Feedback is undefined when a response matches several sections

Location: docs/question-types/ordering.md:296-298

A response that matches an accepted or a rejected answer shows that section's
feedback, if it declares one.

Description: Two ## [accept] sections with the same lines (duplicate-alternative-lines) and an accept that repeats the [ordering] block (accept-repeats-answer-key) are warnings, not errors, so a valid question can have several sections that match one response, each with its own feedback. The spec does not say which feedback is shown: the first, all, or none (the answer key has no feedback).

Impact: Implementations show different feedback for the same response.

Suggested fix: State a precedence rule, for example: the [ordering] block first, then sections in document order; the first match decides the score and the feedback.

medium F42: Indentation step offered to the student under strict is not defined

Location: docs/question-types/ordering.md:261-272

A line's **indentation level** is its leading whitespace divided by that unit,
and that level -- not the raw whitespace -- is what a response carries and
what `"strict"` compares.

Description: The unit is the GCD over every section, so a single distractor or accepted line indented by 2 spaces moves 4-space answer-key lines to levels 2 and 4 (examples/valid/ordering/indentation-unit-across-sections.yaml). The spec does not say what one indentation step in the student interface is (one unit, or a code-level indent), nor that adding a section can change the levels of the answer key and of stored responses.

Impact: Under strict, a student who indents a loop body once submits level 1 while the key expects level 2; responses stored before a section was added stop matching.

Suggested fix: State that the interface moves a line by one unit per step and renders levels with the inferred unit, or derive the unit from the [ordering] block alone and lint other sections that do not fit it.

low F17: Indented blockquotes in observations are implementation-defined

Location: docs/question-types/ordering.md:234-237

It is up to the implementation to decide if it should ignore the indentation,
issue a warning or even an error.

Description: The grammar (ordering.md:153-154) accepts ws? before > and !, while the prose lets implementations reject it. Indentation of 4 spaces or more also makes an indented code block in CommonMark, as the example shows. The same document can parse or fail depending on the implementation.

Impact: Portability of documents between implementations.

Suggested fix: Fix one behavior: accept up to 3 spaces of indentation, as CommonMark does, and lint it.

low F35: An empty tolerance object is neither forbidden nor covered by missing-tolerance

Location: docs/question-types/numeric.md:215

| tolerance          | info     | missing-tolerance              | should be defined for a `decimal` or `fraction` answer[^5]         |

Description: schema/numeric.yaml:68-90 allows tolerance: {}. The rule says the tolerance "should be defined"; lint-codes.md:37 says "No tolerance is given". mdq-py reports nothing for {answer: 2.5, tolerance: {}}, while the same question without the key reports missing-tolerance.

Impact: An empty tolerance hides the lint without adding any tolerance.

Suggested fix: Require at least one property in the schema (minProperties: 1), or state that an empty tolerance counts as missing.

low F44: Whitespace and list markers in line text are not specified

Location: docs/question-types/ordering.md:165-166

If it is a `ul` list, the question infers `content: "text"`. Each line is
derived from the respective list item, preserving its markdown source verbatim.

Description: "Markdown source verbatim" does not say whether the list marker and the space after it are part of the text (they are not, in the corpus), or whether trailing whitespace is kept. For code lines, the spec says nothing about trailing whitespace either, and it is compared by content.

Impact: A line with a trailing space can be different from the same line without it in one implementation and equal in another.

Suggested fix: State that the text excludes the marker and its following whitespace, and whether trailing whitespace is stripped for both content types.

low F45: Language of ## [accept] and ## [reject] fences is not addressed

Location: docs/question-types/ordering.md:193-194

The highlight of fenced code blocks is ignored.

Description: The sentence sits in the ## [extra] section. The accepted/rejected section only says the content block must have the same type. Nothing says whether a fence language in ## [accept] or ## [reject] is ignored, must match highlight, or is an error.

Impact: A different fence language in an alternative can be accepted, warned or rejected depending on the implementation.

Suggested fix: Move the sentence to the Body section and make it apply to every section after [ordering].

low F47: "Never shown that order" conflicts with a random shuffle

Location: docs/question-types/ordering.md:7-9

Students are never shown that order --
implementations MUST present the lines shuffled, in a random or pseudo-random
arrangement

Description: A random permutation can equal the answer key, especially for two or three lines (1 in 2 for the minimum of two lines). The text says both "never" and "random" without saying whether an implementation must reshuffle in that case.

Impact: An implementation that follows "random" literally can show the solution.

Suggested fix: Say that implementations MUST NOT present the answer key's order, and reshuffle when the permutation equals it.

Location: docs/question-types/ordering.md:203-212

The accept/reject blocks start with a `## [accept]` or `## [reject]` header,

Description: Nothing says an accepted or rejected ordering must use only lines from [ordering] plus ## [extra], nor how many copies. medium F28: The spec never states what the domain does to responses

Location: docs/question-types/numeric.md:112-117

If not given in the frontmatter, the domain is inferred from how the value and
the absolute tolerance are written

Description: "Number type/domain" explains how the domain is inferred, but numeric.md never says what the domain means for grading. The effect lives only in responses.md:133-134 (a decimal response to an integer question is malformed) and in examples/grading/numeric.yaml ("Exact integer": 1822.5 is malformed; "Fraction": 0.3333 scores 0 for 1/3, so a fraction question accepts decimals). Impact: A reader of numeric.md cannot tell that [numeric]: 42 +- 5% rejects the response 43.5 as malformed even though it is inside the tolerance.

medium F30: A frontmatter unit that disagrees with the tag unit is silently dropped

Location: docs/question-types/numeric.md:22

| unit          | string    | Unit of the response, if given                  |

Description: numeric.md does not say what happens when the frontmatter unit and the [numeric(unit)] tag disagree. The generic rule of question-base.md:109-110 (frontmatter wins) applies, and examples/valid/numeric/frontmatter-unit-wins accepts unit: kg with [numeric(g)]: 60 +- 1 with no diagnostic. short-answer.md:95 makes the analogous body/frontmatter collision an error (conflicting-accept).

Impact: A question whose body says grams is graded in kilograms, with no warning; numeric and short-answer treat collisions differently.

Suggested fix: Specify the collision in numeric.md and report it, at least as a warning, when the two units differ.

medium F31: Mapping from the body to answer and tolerance is not specified

Location: docs/question-types/numeric.md:145-150

* Relative tolerance: The response is accepted if `|answer - response| ≤ tol`,

Description: numeric.md never declares the answer and tolerance fields nor says that the body value becomes answer, +- x becomes tolerance.absolute and +- x% becomes tolerance.relative divided by 100. The frontmatter table (line 19-24) lists neither, and mdq-py reports both as unknown-frontmatter-key in the frontmatter. Line 150 uses the body percentage (÷ 100), footnote 2 (line 217) uses the stored fraction (|answer| ⨉ relative); only the comment of examples/valid/numeric/tolerances.yaml states that 5% becomes 0.05.

Impact: Implementers must reverse-engineer the data form from the schema and the corpus; a relative: 5 written for 5% is a likely error.

Suggested fix: Add a section that maps each body part to its field, with tolerance.relative = percentage / 100, and use one form in the formulas.

medium F40: Mapping from the ordering body to lines, extra, accept and reject is not specified

# [Spec] Numeric: one rule for response units

**Labels:** high, medium

## Problem

responses.md lets implementations convert a response unit, then calls any other unit malformed, and says an incompatible unit is both rejected and graded zero. numeric.md also drops a frontmatter `unit` that disagrees with the tag unit with no diagnostic.

Options: (A, recommended) same unit is valid, a convertible unit is converted before grading, any other unit is a `ResponseError`; plus a warning when frontmatter and tag units differ. (B) only the declared unit is valid, and unit conversion is removed from the spec.

## Evidence

- `docs/responses.md:129-135`: A response unit other than the declared one is both convertible and malformed

  ```
  Implementations MAY do unit conversions and rewrite the response to a canonical
  form, but they MUST reject a response with a unit that is not compatible with
  the question's unit with grade zero.
  
  A value the question cannot represent is a malformed response, never a wrong
  answer: a decimal where `domain` is `integer`, or a unit other than the
  declared one.
  ```
- `docs/question-types/numeric.md:22`: A frontmatter `unit` that disagrees with the tag unit is silently dropped

  ```
  | unit          | string    | Unit of the response, if given                  |
  ```

## Impact

- **A response unit other than the declared one is both convertible and malformed:** For `[numeric(g)]: 1000` and the response `{value: 1, unit: kg}`, one implementation scores 1, another raises `ResponseError`. For `{value: 1, unit: s}`, one scores 0 and another raises an error.
- **A frontmatter `unit` that disagrees with the tag unit is silently dropped:** A question whose body says grams is graded in kilograms, with no warning; numeric and short-answer treat collisions differently.

## Suggested fix

- **A response unit other than the declared one is both convertible and malformed:** State one rule: a unit equal to the declared one is valid; a different unit that the implementation can convert is converted before grading; any other unit is a malformed response (`ResponseError`), not a zero. - [ ] "with grade zero" no longer appears next to "reject"
- [ ] A lint code reports a frontmatter `unit` that differs from the tag unit, with a corpus example
